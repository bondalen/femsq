Решение 009: Обходник связей — отдельный слой, кандидат в feQuLib (`FemsqWalkTree`)

Дата: 2026-08-18  
Последнее обновление: 2026-08-18  
Статус: ✅ Принято  
Участники: Александр

Проблема

`FemsqTree` в feQuLib рисует дерево, но не обходит связи БД. В FEMSQ появилась обёртка `RelationTree`: JSON экземпляра + lazy expand + карточка детали. Её уже планируют два экрана (КСДСФ и Договоры/СФ). Тот же механизм нужен другим проектам. Если оставить обходник «проектным» и связанным с GraphQL FEMSQ, в следующем продукте появится параллельный код — та же боль, из‑за которой выносили `FemsqTable` (Решение 008).

Рассмотренные варианты

1. Расширить `FemsqTree` JSON-спекой и fetch

    Плюсы: один импорт.
    Минусы: renderer начинает знать рёбра, кардинальность, сеть. Ломает контракт v1 (feQuLib **0016**): lib не копирует дерево и не ходит в API.

2. Держать обходник только в FEMSQ без отвязки от хоста (status quo среза 1)

    Плюсы: быстрее закрыть КСДСФ.
    Минусы: `RelationTree` импортирует `@/api/relation-api` и каталог `invNum.inv`; второй проект копирует файл целиком.

3. Отдельный компонент-обходник; в FEMSQ сразу контракт lib; вынос в feQuLib после второго потребителя (выбрано)

    Плюсы: `FemsqTree` остаётся глупым; walker переиспользуем; каталог/SQL/JSON экранов остаются у хоста.
    Минусы: один лишний слой; вынос в lib — отдельный чат, не сейчас.

Решение

Три слоя, не два:

| Слой | Имя сейчас | Куда |
|---|---|---|
| Renderer | `FemsqTree` | feQuLib **0016**, не расширять ради обхода |
| Walker | `RelationTree.vue` + `relation-tree.ts` | FEMSQ до выноса; целевое имя в lib — `FemsqWalkTree` |
| Хост | JSON экземпляра, каталог рёбер, GraphQL/SQL, экраны | навсегда в продукте |

Правила реализации:

1. **T4b (обязателен до T7 и до полного JSON КСДСФ):** walker принимает `fetchNode` / `fetchExpand` снаружи; в JSON ребёнка поле `to` (таблица назначения); чистые функции не читают `RELATION_EDGES` и не импортируют Apollo. Иначе второй экран FEMSQ копирует связанный код.
2. **T8** — только дыра контракта `FemsqTree` (renderer). Не путать с выносом walker.
3. **T9** — вынос в feQuLib отдельным чатом **после T7** (два живых потребителя в FEMSQ) **или** когда второй продукт берёт дерево. Backend-каталог Java / `relationNode` в lib **не** выносить.
4. Не класть в walker Excel, очередь СУДЗ, формы CRU.

Архитектурные соображения:

    Контракт walker: `spec` + `rootId` + колбэки fetch. Имена рёбер — непрозрачные строки.
    Хост FEMSQ: `relation-api.ts`, `RelationEdgeCatalog`, `ksdsf-inv-num.tree.json`, `contracts-inv.tree.json`.
    Форма GraphQL `{ key, fields { name value } }` — удобный образец для другого хоста, не часть feQuLib.

Последствия

Положительные:

    ✅ Второй экран FEMSQ и другой проект подключают тот же алгоритм без копирования SQL/СУДЗ.
    ✅ `FemsqTree` v1 не раздувается.
    ✅ Решение 008 сохраняется: UI-переиспользование — через feQuLib, не через копипасту FEMSQ.

Отрицательные:

    ⚠️ До T4b код среза 1 ещё связан с FEMSQ — окно для регресса, если сразу писать T5/T7.
    ⚠️ Имя `RelationTree` в FEMSQ временное; при T9 — `FemsqWalkTree`.

Альтернативы на будущее

    Java-модуль «whitelist рёбер + JDBC expand» — только если появится второй Spring-хост с тем же паттерном.
