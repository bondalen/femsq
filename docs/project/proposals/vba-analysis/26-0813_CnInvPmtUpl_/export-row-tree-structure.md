## 1. Повод и симптомы на экране КСДСФ

### 1.1. `doc / link` в Excel-кандидате

В карточке Excel-кандидата для платежей поля DTO долга переиспользуются как алиасы:

| UI | Поле DTO | Источник Tbl |
|----|----------|--------------|
| doc | `cidutDoc` | `ciputCnInvDocCode` ← колонка **«№ докум.»** |
| link | `cidutLink` | `ciputLink` ← колонка **«Ссылка»** |

Это не номер счёта-фактуры и не «Присвоение». Искать в Excel нужно в колонках U («№ докум.») и I («Ссылка»), а не в J («Присвоение»).  
`ciputSheetNum` — индекс листа книги, не номер строки файла.

### 1.2. Пять строк «б/н» и одна карточка очереди

В пакете 59 у номера «б/н» в Tbl попали пять белых строк (жёлтые итоги без «№ докум.» не загружаются):

| Строка файла | `ciputKey` | Договор | № докум. | Ссылка | Сальдо |
|-------------:|-----------:|---------|----------|--------|-------:|
| 60 | 141437 | КС-14 | 5900202347 | 115969 | 0 |
| 62 | 141438 | КС-14 | 5400199014 | б/н | 0 |
| 64 | 141439 | КС-14 | 5400224218 | б/н | −10 427 623,46 |
| 5805 | 144503 | КС-51 | 5900210215 | 114968 | 0 |
| 5807 | 144504 | КС-51 | 5400200664 | (пусто) | 0 |

Очередь КСДСФ (`rebuildPmtUplSfDouble`) склеивала их **только по номеру СФ** (`LTRIM(ciputCnInv)`), без договора. Представитель карточки — `MIN(ciputKey)` → строка 60 (КС-14, doc 5900202347). Лес документов показывал код 5400224218 (строка 64) — единственный из пяти, у которого уже есть `cn_inv_pm` в истории.

### 1.3. Свёртка в Access

Access при Excel→`CnInvPmtUplTbl` **не** схлопывает строки и **не** читает цвет: в Tbl идёт каждая непустая ячейка «№ докум.».  
Свёртка для решения «какой это СФ» — позже: **кредитор + договор + номер** (`cipuCn_CtptCnOneInv`). Платёжные строки остаются по одной на строку Excel.  
На КС-14 «б/н» и КС-51 «б/н» Access считал бы двумя отдельными ONE-совпадениями (у каждого договора ровно один такой `cnInv`), а не одной глобальной TwoLoad-группой из пяти строк.

## 2. Дерево строк традиционной раскладки

Книга имеет группировку строк Excel (`outlineLevel`). Для классических `export_*` (A–Z, якорь «№ докум.» = U):

| Уровень | Роль | Признак на строке |
|--------:|------|-------------------|
| 4 | **Платёжный документ** (белая) | Непустой «№ докум.»; заполнены договор, присвоение, стройка, срок |
| 3 | **Жёлтый итог** группы платежей одного срока | Пустой «№ докум.»; есть срок и сальдо; **нет** договора / присвоения / стройки |
| 2 | Итог кредитора | Без срока |
| 1 | Итог счёта ГК | |
| 0 | Общий итог | |

Договор, счёт-фактура и стройка **не имеют** собственных итоговых строк — они живут только на уровне 4.

### 2.1. Пример (пакет 59, `0620CR000478`)

```
КС-51                          ← колонка на документе, не узел outline
└─ 0620CR000478                ← СФ файла (кредитор + договор + присвоение)
   └─ 051-2004018              ← группа стройки (сплошной отрезок)
      ├─ 28.02.2026  [жёлтая 9103]  → 5400218049
      ├─ 31.12.2025  [жёлтая 9105]  → 8800587334
      ├─ 28.01.2026  [жёлтая 9109]  → 5100009811 … 5100009813
      └─ 28.02.2026  [жёлтая 9113]  → 8800587334, 5400218044, 5400218048
```

Два вхождения срока 28.02.2026 **не сливать**: у каждого своя жёлтая строка и свой набор документов. Отдельного кода объекта за второй жёлтой строкой в колонках нет — это повтор открытия итога уровня 3 после промежуточных сроков. Порядок внутри стройки не хронологический.

### 2.2. Непрерывность узлов (файл 59)

| Узел | Непрерывность на листе |
|------|------------------------|
| Группа стройки (кредитор+договор+номер+CAC) | всегда сплошная (5 648 отрезков) |
| СФ файла (кредитор+договор+номер) | у 21 номера куски разнесены (напр. «24CR0244» — 17 жёлтых групп) |
| Группа платежей одного срока (= одна жёлтая L3) | 7 575; повтор одного ключа «стройка+срок» — 1 случай (`0620CR000478` / 28.02.2026) |

Жёлтая строка определяется **без цвета**: пустой «№ докум.», непосредственно перед ней ≥1 белая, сальдо = сумма сальдо белых (ε = 0,01), срок совпадает. Цвет (indexed 43) общий у жёлтых L3 и части верхних итогов — по желтизне уровни не различить.

### 3.2. Нетрадиционная (QII, 26-0817 / 767501 и 767502)

- Есть «Опер.сегмент», «Вид контрагента», сальдо начальное, обороты.
- Документ на уровне **7**; ближайший итог — уровень **6** (закрывает стройку договора, а не срок).
- Внутри L6 у 767501 «Присвоение» разное в 180/279 итогах; у 767502 меняются и договор, и присвоение.
- `*.remapped_canon.XLSX` повторяет заголовки традиционной книги, но outline снят, «Срок оплаты» пуста во всех строках — группу срока из неё не восстановить.
- Аналоги традиционной раскладки за **тот же** срез 26-0817 для 767501/767502 на шаре нет; есть только за 26-0130/26-0422.

## 4. Сущности и ключи

### 4.1. Уже в предметной модели / БД

| Сущность | Ключ / место |
|----------|--------------|
| Договор | `ags.cn` / номер в Excel «Договор» |
| Счёт-фактура | `ags.inv` + `invNum` + связь `cnInv` |
| Платёжный документ (каталог) | `ags.cn_inv_doc` (`cn_inv_doc_kod`) |
| Платёж | `ags.cn_inv_pm` (стройка `constract_code`, срок `cn_inv_pm_due`) |

Принимающую схему платежей **менять не требуется**: стройка для долга определяется строкой платежа.

### 4.2. Сущности файла, отсутствующие как таблицы БД

| Сущность | Как задаётся в традиционной раскладке | Нужна ли таблица в `ags` |
|----------|--------------------------------------|---------------------------|
| **СФ файла** | кредитор + договор + присвоение (настоящий номер) | нет — совпадает с правилом Access |
| **Группа стройки** | СФ файла + код стройки; сплошной отрезок L4 | нет для основной задачи; ключ в staging |
| **Группа платежей одного срока** | документы одной жёлтой L3; срок — атрибут | нет; ключ в staging |

### 4.3. Промежуточные ключи загрузки (предложение)

В `sudz.CnInvPmtUplTbl` (или эквивалент) при проходе листа проставлять на каждую белую строку:

1. ключ СФ файла (для настоящих номеров);
2. ключ группы стройки;
3. ключ жёлтого итога (не путать со сроком: два итога одной даты — два ключа).

Сами жёлтые строки и итоги кредитора в Tbl **не** писать (как сейчас и в Access).

### 4.4. Свёртка очереди КСДСФ

Два разных шага:

1. **Как Access:** кредитор + договор + номер — убирает смешение КС-14 с КС-51 по одному «б/н».
2. **Не** делать карточку на каждый жёлтый итог по умолчанию: у номерного СФ это размножит группы сроков/строек.

## 5. Подозрительные номера СФ

### 5.1. Класс

Узкий набор «пустых» номеров: пусто, `б/н` / `Б/н` / `БН`, `Б/С`, `-`, `*`.  
Короткие числа (`92`, `14`) — обычные номера, не этот класс.

### 5.2. Поведение

Стандартное правило «кредитор + договор + номер» даёт **один** СФ на договор. История так и хранится (на КС-14 «-» и «б/н» уже собрали много строек и сроков каждый).

Разные стройка или срок **не** означают автоматически другой СФ: у настоящего номера `0620CR000478` разные сроки — внутренние группы одного СФ.

Для очереди / советника стройка и срок — **фильтр поиска** среди существующих СФ с таким номером на договоре, а не доказательство нового СФ. Если подходят несколько — строка остаётся в очереди.

Пара строк с одной суммой документа и префиксами `59`/`54` (как 60+62) — сходство с соседними номерными СФ на той же стройке, **не** ключ записи в базу.

## 6. Номер платёжного документа

| Утверждение | Факт по `ags` (снимок разбора) |
|-------------|--------------------------------|
| Номер уникален глобально | **Нет.** Каталог: 234 807 строк / 234 756 кодов (51 дубль ключей). |
| Номер уникален в истории платежей | **Нет.** Один код на нескольких СФ: 35 191; на нескольких договорах: 6 038. |
| Пара «номер + дата документа» — ключ строки | **Нет.** Внутри одного пакета эта пара повторяется (до 4 строк); у части пар разные сроки. |
| Номер «переезжает» между СФ по пакетам | Да — типичный перенос документа, не второй документ с тем же кодом. |

Пример из файла 59: код `8800587334` в двух группах срока одного СФ; код `5400224218` в истории сидел на других СФ КС-51, в пакете 59 — на «б/н» КС-14.

## 7. Выводы для загрузки

**План исполнения:** [chat-plan-26-0922 §1.13 / §2.7](../../../../development/notes/chats/chat-plan/chat-plan-26-0922-pmt-upl-ui-complete.md).

### 7.0. Принято (лист 1.13.0, 2026-10-03)

Три обязательных правила для традиционной раскладки (код ещё не начат):

| # | Правило | Куда |
|---|---------|------|
| **A** | Свёртка решения о СФ и очереди КСДСФ = Access: **кредитор + договор + номер**. Не группировать только по номеру. Карточки КСДСФ **не** плодить на каждый `due_grp`. | rebuild / агрегаты / лес — **1.13.4** |
| **B** | При Excel→Tbl на **белых** строках писать промежуточные ключи: СФ файла, отрезок стройки, жёлтый итог (в т.ч. порядковый `due_grp` 1…n внутри пакета+СФ+CAC+срок). Жёлтые строки в Tbl **не** писать. Цвет заливки не использовать. | staging — **1.13.1** |
| **C** | В домене только **ADD** nullable `ags.cn_inv_pm.cn_inv_pm_due_grp` (smallint/tinyint): номер жёлтой группы срока. Почти везде `1`; два жёлтых итога одного срока (кейс `0620CR000478` / 28.02.2026) — `1` и `2`. Старые строки `NULL`. Отдельные таблицы групп в `ags` **не** создавать. `cn_inv_pm_cac_grp` — опционально, не блокер. | DDL + InsPm — **1.13.2–1.13.3** |

Дополнительно (не блокируют A–C): подозрительные номера — **1.13.6**; Excel-кандидат со всеми белыми строками кейса — **1.13.5**; QII — **1.13.7**.

### 7.1. Традиционная раскладка (следствия A–C)

1. `constract_code` / `cn_inv_pm_due` на платеже остаются; `due_grp` дополняет их, когда один срок встречается в нескольких жёлтых итогах.
2. Подозрительные номера (`б/н`, `-`, …) правилом A дают один СФ на договор; жёлтая/срок **не** автосоздают новый СФ.
3. Критерии приёмки пакета 59 — план §2.7.

### 7.2. Нетрадиционная раскладка

Для **настоящего** номера СФ: читать ключ с строки документа (кредитор + договор + присвоение); итог L6 **не** считать границей СФ.  
Стройка на документ есть → основная задача «стройку для долга» сохраняется.  
Хуже традиционной: нет группы срока; для подозрительных номеров нет сверки по сроку.  
Переложенная `remapped_canon` срока не восстанавливает.  
В плане 0922 — лист **1.13.7** (отложено).

## 8. Замечания по UI (из того же разбора)

- Excel-кандидат платежей целесообразно показывать колонками как в Excel (без сдвоенных подписей) и со **всеми** белыми строками кейса, а не только `MIN(ciputKey)`.
- Агрегаты сальдо и список кодов леса не должны склеивать разные договоры только по номеру СФ.
