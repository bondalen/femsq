## 0. Зачем этот документ

После S73 известно **рабочее число «долгов СФ»** и правило зерна  
`(iKey, ciaNameNull) ≈ (idInv, idNum)`. Цель — **однократный cutover** старой структуры в новую и отказ от долгого dual-read.

**Уточнение v0.2 (владелец, 2026-08-27):** перенос **нельзя** планировать «только слоты, `Dbt` потом». Канон `Dbt` обязателен в модели (08 / M2); отложить его в cutover — риск второго переноса и снова тянуть `ciaKey` (cmm, отчёты). Поэтому **сначала тщательно обсудить `Dbt` (без UI)**, затем репетировать полный перенос на **DEV**, параллельно шлифуя этот документ под prod.

Сегм. 21 («`DbtValue` в воронке до чекбокса `Dbt`») относится к **текущей загрузке свода**, не отменяет включение `Dbt` в **разовый seed**.

## 0.1. Порядок разработки (согласованный каркас)

В плане чата: **[S74 M1–M6](../development/notes/chats/chat-plan/chat-plan-26-0802-sudz.md#s74--трек-cutover-m1m6--2026-08-27)**.

```
M1  Обсуждение Dbt (без UI)     → решения в 08 / 04-3 / этот док
M2  DEV: перенос old→new        → invDbt + Dbt + invDbtDbt (+ Value/мост cia)
    └─ параллельно фиксируем порядок для prod (этот документ)
M3  Calm F1 (sum→слот)          → после появления слотов/истории на DEV
M4  Экран двоящих + чекбокс 7   → доработка уже на заполненной новой структуре
M5  Остальные чекбоксы воронки  → до завершения процесса загрузки свода
M6  Prod survey → MSSQL2012 → окно H
```

**Не раздувать** экран/7-й чекбокс «в пустой» новой модели до M2 — иначе снова слепой Create и dual-логика.

### 1.4. Резолв `cnNum` / `invNum` для `invDbtVar` при историческом seed (2026-08-27)

**Проблема:** у `cia` однозначны `cn_s_org` и `accnt` (`cias`); `cn`/`inv` — тоже; но **`cnnKey` / `inKey`** среди нескольких номеров у того же `cn`/`inv` из строки `cn_inv_dbt` **не** выводятся (десяток фактов на DEV: варианты написания / смена № во времени).

**Канон (без ручной очереди):** для `(cia, upl)` с `asOf = uplStatusOnDate` (иначе `upl_date`):

| Поле | Правило |
|------|---------|
| `idvvAccnt` / `idvvCn_s_org` | из `cias` / `cia` |
| `idvvInvNum` | среди `invNum` этого `iKey` с `inTimeOfEntry ≤ asOf` — **max** `(inTimeOfEntry, inKey)`; если таких нет — **earliest** номер на `iKey` (fallback) |
| `idvvCnNum` | среди `cnnType=1` этого `cn` с `cnnTimeOfEntry ≤ asOf` — **max** `(cnnTimeOfEntry, cnnKey)`; иначе earliest type=1 |

**Живая воронка:** по-прежнему предпочтителен текст Excel (`cidutCnName` / `cidutCnInv`) при однозначном match; временнóе правило — для seed / отсутствия текста.

**Проверка на DEV (2026-08-27):** multi `iKey` `1570,6912,7013,7081,19695,40336`; multi `cn` `743,1151,1192,1945` — детерминированные переключения (лат./кир., б/н→№, точки, `БН`→`Б/Н` и т.п.); ручной разбор не требуется. Нюанс: у части номеров `TimeOfEntry` = дата заведения в FishEye (часто 2022-01), поэтому старые asOf часто идут в fallback earliest.

### 1.5. Concurrent multi-cia → отдельные `invDbt` (обязательно в seed / prod)

**Симптом (M2 DEV):** 13 пар `cn_inv_dbt` на одном зерне S73 (unnamed) в одной upl → `UNIQUE(dvInvDbt,dvUpl)` оставлял одну сумму → **занижение/искажение** итога свода и СГК.

**Причина:** несколько `cia` с пустым `ciaName` склеены в один слот; СГК в парах **одинаковый**; `cn_s_org` разный (часто одно юрлицо, разные dated-строки).

| Класс | Суть | Пример DEV |
|-------|------|------------|
| **A** | Один cn + один СФ; недоразмеченный P2 | iKey 3867, 4766, 14920, … |
| **B** | Один `inv` на два cn одной орг.-исполнителя (переезд) | **40665** (`41104-23-…` / `41104-24-…`, ИНН 2309001660) |

**Правило seed (D4a):** если через мост cia→слот в одной upl ≥2 строк `cn_inv_dbt` на один слот — `min(ciaKey)` остаётся; остальным cia — новый `invDbt` (`idNum` ≥241), новый `Dbt` (`dbtNote` `M2-concurrent-cia` или `M2-cn-migrate` для класса B), обновление моста. Затем E1 без потерь.

**На prod:** тот же шаг после D4, до E; N_split пересчитать (не хардкодить 9). VERIFY: `COUNT(DbtValue)=COUNT(cn_inv_dbt)` и 0 групп `(slot,upl)` с COUNT>1.
