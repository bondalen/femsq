## 0. Зачем

Канон (`rebuildDbtUplCstAg` / Access `fnCiasDbtUplCst`) пишет стройку **только** при ровно одном `cnipCstAgPn` в pm ∩ `g_p`@upl. Иначе — пусто (FEMSQ) или `'строек: N'` (Access). После QI/QII на DEV остаются **multi** и **empty**; часть multi — передача объекта агенту (023-… → 051-…) в пределах одной выгрузки.

**Цель эксперимента:** для **каждого** долга с Value@upl всегда заполнять отображаемый код стройки (и метку правила в «наименовании»), **не меняя** канон `DbtUplCstAg`, пока не изучены результаты.

**Вне scope:** правка канона H6; прод; замена сверки Access FAIL=0; UI воронки D; бэкфилл S80.

## 1. Каскад (утверждённая логика)

| Шаг | Условие | `duexCode` | `duexName` (эксперимент) | `duexCstAgPn` |
|-----|---------|------------|--------------------------|---------------|
| **1.1** | ровно 1 код в pm ∩ `g_p`@upl | код как канон | `1.1 g_p` | ключ |
| **1.2a** | >1 в `g_p`; фильтр по агенту pm → 1 | этот код | `1.2 agent` | ключ |
| **1.2b** | >1; агент не схлопнул | склейка кодов | `1.2 multi` | NULL |
| **1.3a** | в `g_p` **0** кандидатов; вне `g_p` ровно 1 | код | `1.3 out-gp` | ключ |
| **1.3b** | в `g_p` 0; вне `g_p` >1 | склейка | `1.3 multi` | NULL |
| **1.4** | нигде нет | `не обнаружена в платежах` | `1.4 none` | NULL |

**Правила:**

- **1.3 только если в `g_p` кандидатов 0** (после multi@`g_p` — склейка 1.2b, снаружи не искать).
- Склейка: `код1; код2` (сортировка), не только `строек: N`.
- Агент (1.2): БУиРГ с `cn_inv_pm.csoCn_s_org_smpl` ↔ БУиРГ агента кандидата (`cstAgPn`→`cstAg`→`ogAg`). NULL / 9999999 на pm не голосуют.
- Горизонт 1.3: сначала pm любых `pm_upl`, связанных через `g_p` с **любым** `dbt_upl` того же `yr`; если пусто — те же пути матча без лимита года. В `duexDetail` — какой горизонт сработал.
- Матч-пути — как канон (`raw_cia` ∪ `raw_doc`), см. `JdbcSudzDao.sqlDbtUplCstAgRawCte`.

## 2. Хранение (рядом с каноном)

Канон `sudz.DbtUplCstAg` (`ducaCstAgPn int NOT NULL` + FK) **не трогать**.

```text
sudz.DbtUplCstAgExp (
  duexDbt, duexUpl,           -- PK
  duexRule     tinyint,       -- 11 / 12 / 13 / 14 (+ подтипы a/b в Detail или отдельные коды)
  duexCstAgPn  int NULL,      -- только при однозначном выборе
  duexCode     nvarchar(...), -- → *_CstAgPnCode в exp-витрине
  duexName     nvarchar(...), -- на эксперимент: метка правила
  duexDetail   nvarchar(...)  -- опц.: ключи / горизонт 1.3
)
```

Логика — **хранимка** (предпочтение владельца):

```text
sudz.usp_RebuildDbtUplCstAgExp @dbtUpl int
```

- DELETE/INSERT только в `DbtUplCstAgExp` для `@dbtUpl`
- сводка counts по `duexRule` → блок в `cidufOpsProgress` (или отдельный лог)
- пакет SQL: `docs/development/notes/sql/26-0921-sudz-dbt-upl-cst-ag-exp/` + **`MSSQL2012/`** (без `CREATE OR ALTER` / `DROP IF EXISTS`)

Java: опционально кнопка/флаг «эксперимент» → вызов proc; канон H6 без изменений.

Витрина: `vw_Yr_DbtFactExp` (или COALESCE Exp поверх канона) — **отдельный** asOf-файл `…_cstExp`, не смешивать со сверкой Access.
