## 0. Зачем

Канон (`rebuildDbtUplCstAg` / Access `fnCiasDbtUplCst`) пишет стройку **только** при ровно одном `cnipCstAgPn` в pm ∩ `g_p`@upl. Иначе — пусто (FEMSQ) или `'строек: N'` (Access). После QI/QII на DEV остаются **multi** и **empty**; часть multi — передача объекта агенту (023-… → 051-…) в пределах одной выгрузки.

**Цель эксперимента:** для **каждого** долга с Value@upl всегда заполнять отображаемый код стройки (и метку правила в «наименовании»), **не меняя** канон `DbtUplCstAg`, пока не изучены результаты.

**Вне scope:** правка канона H6; прод; замена сверки Access FAIL=0; UI воронки D; бэкфилл S80.

## 1. Каскад (утверждённая логика)

| Шаг | Условие | `duexCode` | `duexName` (эксперимент) | `duexCstAgPn` |
|-----|---------|------------|--------------------------|---------------|
| **1.1** | ровно 1 код в pm ∩ `g_p`@upl | код как канон | `1.1 g_p` | ключ |
| **1.2a** | >1 в `g_p`; фильтр по агенту pm → 1 | этот код | `1.2 agent` | ключ |
| **1.2b** | >1; агент не схлопнул | склейка кодов | `1.2 multi` | NULL |
| **1.3a** | в `g_p` **0** кандидатов; вне `g_p` ровно 1 | код | `1.3 out-gp` | ключ |
| **1.3b** | в `g_p` 0; вне `g_p` >1 | склейка | `1.3 multi` | NULL |
| **1.4** | нигде нет | `не обнаружена в платежах` | `1.4 none` | NULL |

**Правила:**

- **1.3 только если в `g_p` кандидатов 0** (после multi@`g_p` — склейка 1.2b, снаружи не искать).
- Склейка: `код1; код2` (сортировка), не только `строек: N`.
- Агент (1.2): БУиРГ с `cn_inv_pm.csoCn_s_org_smpl` ↔ БУиРГ агента кандидата (`cstAgPn`→`cstAg`→`ogAg`). NULL / 9999999 на pm не голосуют.
- Горизонт 1.3: сначала pm любых `pm_upl`, связанных через `g_p` с **любым** `dbt_upl` того же `yr`; если пусто — те же пути матча без лимита года. В `duexDetail` — какой горизонт сработал.
- Матч-пути — как канон (`raw_cia` ∪ `raw_doc`), см. `JdbcSudzDao.sqlDbtUplCstAgRawCte`.

## 2. Хранение (рядом с каноном)

Канон `sudz.DbtUplCstAg` (`ducaCstAgPn int NOT NULL` + FK) **не трогать**.

```text
sudz.DbtUplCstAgExp (
  duexDbt, duexUpl,           -- PK
  duexRule     tinyint,       -- 11 / 12 / 13 / 14 (+ подтипы a/b в Detail или отдельные коды)
  duexCstAgPn  int NULL,      -- только при однозначном выборе
  duexCode     nvarchar(...), -- → *_CstAgPnCode в exp-витрине
  duexName     nvarchar(...), -- на эксперимент: метка правила
  duexDetail   nvarchar(...)  -- опц.: ключи / горизонт 1.3
)
```

Логика — **хранимка** (предпочтение владельца):

```text
sudz.usp_RebuildDbtUplCstAgExp @dbtUpl int
```

- DELETE/INSERT только в `DbtUplCstAgExp` для `@dbtUpl`
- сводка counts по `duexRule` → блок в `cidufOpsProgress` (или отдельный лог)
- пакет SQL: `docs/development/notes/sql/26-0921-sudz-dbt-upl-cst-ag-exp/` + **`MSSQL2012/`** (без `CREATE OR ALTER` / `DROP IF EXISTS`)

Java: опционально кнопка/флаг «эксперимент» → вызов proc; канон H6 без изменений.

Витрина: `vw_Yr_DbtFactExp` (или COALESCE Exp поверх канона) — **отдельный** asOf-файл `…_cstExp`, не смешивать со сверкой Access.

## 5a. Политика прода (накопление решений)

### Область поиска для канона: **P1** (принято 2026-09-21)

«Любым способом» в первом каноне = только pm ∩ **`g_p`@этого dbt upl**.

| Корзина | Источник Exp | Код (Rslt) | Наименование | FK |
|---------|--------------|------------|--------------|-----|
| **A** однозначно | **1.1** + **1.2 agent** | `cstapIpgPnN` | `cstName` (из Cst) | заполнять |
| **B** multi | **1.2 multi** | `кодов - N: code1; code2; …` (≤500, сортировка) | `code1 — name1; …` (≤500; обрезка по целым парам + `…`) | NULL |
| **C** нет | всё остальное: **1.4** + бывший **1.3** (вне `g_p`) | `не обнаружена в платежах` | **пусто** (метки правил Exp в прод не тащить) | NULL |

Ориентир DEV @903 при P1: A≈**1670**, B=**6**, C≈**126** (113×1.4 + 13×1.3).

**P2 отложен:** 1.3 (год→all) не входит в первый канон; остаётся в Exp и как опция «добор» после UAT.

**Не корзины:** свёртка Pn→Cst на данных не бывает; `{d}_AgOrg` при B/C = NULL; в наименование прод — только бизнес-текст.

### Горизонт 1.3 (для Exp и будущего P2)

**Принято:** если кандидатов в `g_p`@upl **0** — сначала pm того же `yr`, если пусто — all-time; в аудите `horizon=year`/`all`.  
В **P1** этот горизонт **не влияет** на Rslt (исход → C).

### Хранение канона (DEV ✅ 2026-09-21)

- `ducaCstAgPn` **nullable** (FK только для A);
- `ducaCode` / `ducaName` nvarchar(500);
- `usp_RebuildDbtUplCstAg` — логика P1; **если нет строк `g_p`@upl — no-op** (не затирать S80-бэкфилл @901);
- `vw_Yr_DbtFact` — Code/Name из denorm при наличии строки; AgOrg только при FK;

## 8. Загрузка pm с прод (DEV) — стоп 2026-09-21, продолжение завтра

**Контекст:** для P1@901 нужны `g_p` ← pm 57–60 (Excel с шары `export_26-0130_*`). JAR 307 остановлен; воронка **прервана** на apply InvNot **pm=59**.

| pm | Файл / статус на стопе |
|----|------------------------|
| **57** | ранее ~1180 pm; полный прогон в этой сессии не подтверждён |
| **58** | ✅ воронка done (~11 мин; InsPm 2690) |
| **59** | Tbl 23 521 ✅; InvNot rebuild 5315 / ~2.5 мин ✅; **apply InvNot убит** (~17+ мин построчно); InsPm не дошли |
| **60** | UI успел стартовать после ошибки 59 — **KILL + JAR stop**; состояние ненадёжно |
| 606012 | в zip — свод, не pm (не грузить как платежи) |

**Почему медленно (факт сессии):**

1. `replacePmtUplTbl` ~21.5 мин / 23k — JDBC batch по VPN, длинная транзакция, без mid-progress в UI.  
2. `rebuildPmtUplInvNot` ~2.5 мин — CTE + **глобальный** `GROUP BY invNum.inNumNull`.  
3. `applyPmtUplInvNotLoad` — **главный тормоз:** построчно SELECT alias + 3×INSERT (~5k строк → десятки тысяч RTT).  
4. `InsPmNotLoad` (у 58 ~6 мин) — тяжёлый CTE **дважды** (COUNT + INSERT).  
5. Progress HTML (`cipufLoadingProgress`) пишется **только в конце** воронки → бизнес видит «тишину».

### 8.1 Мероприятия: оптимизация SQL / записи

| # | Приоритет | Мероприятие | Критерий |
|---|-----------|-------------|----------|
| **O1** | P0 | Set-based / чанки `applyPmtUplInvNotLoad` (и аналог dbt) вместо row-by-row JDBC | 5k СФ за минуты, не десятки; лог каждые N строк |
| **O2** | P0 | Сузить `rebuildPmtUplInvNot`: anti-join/count только по кандидатам пакета, не полный скан `invNum` | rebuild ≪ 2.5 мин на 23k Tbl |
| **O3** | P1 | `replacePmtUplTbl`: SqlBulkCopy/TVP или batch 2–5k; индекс `(ciputUnloadKey)` | replace ≪ 21 мин |
| **O4** | P1 | `InsPmNotLoad`: материализовать CTE в `#tmp` → COUNT + INSERT без двойного прогона | один тяжёлый план на пакет |
| **O5** | P2 | Операционно: **один** pm за раз; не авто-цепочка UI; после apply — COUNT left без полного rebuild | нет параллельных воронок |

### 8.2 Мероприятия: логирование / индикация

| # | Приоритет | Мероприятие | Критерий |
|---|-----------|-------------|----------|
| **L1** | P0 | Live flush `cipufLoadingProgress` после каждого шага и каждые N сек / N строк внутри длинных шагов | UI обновляется во время apply |
| **L2** | P0 | Server log **до** шага: `start step`, фазы replace (clear/delete/insert N/M), InvNot `apply i/N`, InsPm start | в `/tmp/femsq-web.log` нет «тишины» >1 мин |
| **L3** | P1 | ETA / «1200/5315» в progress HTML | оператор видит ход без jstack |
| **L4** | P1 | Не блокировать GraphQL 30+ мин: фон + статус по pmKey (или heartbeat в progress) | UI не «завис» |
| **L5** | P2 | Предупреждение при Tbl >10k («ожидаемо долго без O1») | до старта воронки |

**Уже в рабочей копии (не в JAR 307):** стартовые логи шагов воронки; mid-log replace/InsPm/clearDependents — подхватятся после пересборки (завтра вместе с O/L).

### 8.3 Порядок на завтра

1. **L1+L2** (быстро) → пересборка JAR.  
2. **O1** (set-based InvNot apply).  
3. **O2** + **O3** по возможности.  
4. Повторная загрузка **по одному:** дочистить/перезапустить **59** → **60** → при необходимости **57**.  
5. `g_p`@901 → rebuild P1/Exp → анализ (бывший §5 JAR ☐).
