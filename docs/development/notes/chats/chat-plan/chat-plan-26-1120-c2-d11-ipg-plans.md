## 0.1 Метод работы (решение владельца, 2026-11-20)

**Не ломает** общий план вехи и дорожную карту: объём D1.1 и критерий успеха те же. Меняется только **порядок и глубина** внутри C2.

| Было в 0.1.0 (гипотеза агента) | Согласовано с владельцем |
|--------------------------------|---------------------------|
| Shortcut MVP: сразу G3 (LmMn), CRUD ИП позже | Старт с **P2 1.1 (ИП)** → затем планы и далее по этапам |
| Минимум разбора Access до кода | Перед кодом каждого этапа — **тщательное описание Access**, начиная с **UI**, затем VBA/классы/таблицы |

**Цикл на этап (шаблон):**

1. UI Access (формы/подформы, что видно оператору, bound vs код).
2. VBA / классы / записи в SQL Server.
3. Решение migrate: перенести / упростить / оставить в Access до переключения R1 / вне объёма.
4. GraphQL + UI FEMSQ (FemsqTable / паттерны feQuLib).
5. Приёмка этапа на noM6.

Порядок этапов внутри вехи (**ось оператора**, 2026-11-23):  
**O1-foundation (ручной 1.1) → O1 годовая ИП из Excel (структура→пункты, §2.0.1) → O2 планы/лимиты (1.3) → 1.4/2.1.0 по касанию → LdM (уточнение планов, G2) → приёмка D1.1.**

Не смешивать: **годовая ИП (§2.0.1 / O1)** ≠ **LdM (G2)**. Приёмка §2.6 закрыла только **каркас CRUD**, не сценарий «оператор ввёл год с Excel».

Критерий вехи («UtPl@stCost для `_2606`») достигается **после O2**, а не на foundation / O1 — осознанный обмен: сначала полный контур ввода года, затем планы.

## 2.0.2 Модель структуры ИПГ (DAG) и следствия для загрузки — 2026-11-20

Источники: `docs/development/notes/sql/26-0604/docs/01-schema-analysis.md`, Q1–Q4, noM6, Access forms-src `stNetIpg` / `stIpg` / `stNetCost` / `stCost*`, образец `sql_iii.xlsx`.

### Слои данных (актуальное семейство `st`, 2022-04)

```text
ags.st            универсальный узел (stKey, stType)
 ├── stIpg         узел структуры ИПГ (stiKey = stKey, stiType→stType)
 │    └── stIpgNm  имя(ена) узла: stinIpg → stiKey  (! не ipg.ipgKey)
 └── stCost        узел структуры затрат (stcKey = stKey) + stCostNm

ags.stRel         ребро DAG: strParent → strChild  (общий keyspace st)
ags.stNet         именованная схема обхода: stnKey, stnType (1=ИПГ / 2=затраты), stnRoot
ags.stNetPn       какие рёбра входят в схему: stnpStRel + stpnStNet + порядок stpnNum

Привязка к пунктам ИП:
  ipgPn  ←── ipgStPn ──→  stIpg     (у пункта может быть >1 узла: на noM6 ~155 pn с multi-st)

Привязка схемы к ИП / цепи:
  ipg.ipgStRlSh      → stNet (схема ИПГ этой ИП)
  ipgCh.ipgcStNetIpg → stNet (канон для _2606 / fnStDownAll)

Обход: fnSt / fnStDownAll / fnStUpAll(@stNet, @root|@leaf) по рёбрам схемы.
```

**Устаревшее (не использовать):** `ipgSt` / `ipgStRl` / `ipgStRlSh*` — изолированы с 2021, без FK к `ipgPn`.

### Параллель ИПГ ↔ затраты

| | Структура ИПГ | Структура затрат |
|--|---------------|------------------|
| `stType` | 1 «стр. инвестпрограммы» | 2 «стр. затрат» |
| Узлы | `stIpg` + `stIpgNm` | `stCost` + `stCostNm` |
| Схема на DEV | `stNet` 1, **2** (ИПГ) | `stNet` **3** «Стандартная» |
| Access UI | `stNetIpg`, `stIpg` (+ child/parent/`Nm`/`Pn`) | `stNetCost`, `stCost` (+ child/parent/`Nm`) |

Один и тот же механизм `stRel`+`stNetPn`; меняется тип узлов и набор схем.

### Почему это DAG, а не дерево

- В `stRel` у узла бывает **несколько родителей** (напр. `stKey=45` «ПИР и РД»: в `stNet=2` родители **53** и **54** одновременно).
- Разные `stNet` включают **разные** рёбра (тот же 45 в `stNet=1` висит под **2**, в `stNet=2` — под 53/54).
- Лист предметной области: стройка (код САК) + **схема реализации** (`ipgSh`); путь к корню задаётся через `ipgStPn` и может быть **не единственным** (multi-bind `ipgStPn`).

### Версии схемы (`stNet`)

На noM6 сейчас только:

| stnKey | type | Имя | рёбер |
|--------|------|-----|-------|
| 1 | ИПГ | 2021-05, май… | 49 |
| 2 | ИПГ | 2021-12, декабрь. (Утв. 2022) | 83 |
| 3 | затраты | Стандартная | 79 |

Новая инвестпрограмма может потребовать **новую** `stNet` (или расширение `stNet=2`: новые `st`/`stIpg`, рёбра `stRel`, строки `stNetPn`, имена `stIpgNm`). Это не «побочный» шаг загрузки пунктов.

### Имена (`stIpgNm`)

- `stinIpg` → **`stiKey`** (историческое имя колонки путает с ИП).
- У одного узла может быть **несколько** имён (переименование: у `stiKey=44` — «Стратегия информатизации» и «Стратегия цифровой трансформации»).
- Сопоставление с Excel только по строке — неоднозначно без контекста родителя/схемы.

### Сверка «сырой» Excel (`sql_iii`, основной лист) ↔ DEV (грубо)

После снятия нумерации `1.1.1.`:

| | Кол-во |
|--|--------|
| Точное совпадение с `stIpgNm` | ~40 |
| Нечёткое / спорное | ~6 |
| **Нет в DEV** (кандидаты на новые узлы/имена) | **~7** (напр. «Проекты добычи Восточной программы», «План ПИР», разбиение ИБ/КИИ, …) |

Плюс возможны **новые рёбра** даже при старых узлах. Вывод владельца подтверждается: свежие правки структуры в Excel, скорее всего, нужно **перенести на DEV** до/вместе с загрузкой пунктов — отдельным контуром ведения `stNet`/`stIpg`, не тихим lookup в импорте.

### Следствие для алгоритма загрузки (пересмотр §2.0.1 B)

Распознавание `stiKey` для строки Excel — **не** одношаговый lookup. Рабочий контур ближе к:

1. **Сеть:** `cloneStNet` от базовой → ручной diff рёбер/узлов под Excel (не сборка с нуля).
2. **Узел/имя:** match по всем `stIpgNm` (aliases); иначе UI — map (+новое имя) или create.
3. **Привязка:** staging → `ipgPn` + `ipgStPn`; `ipgpSh` = из предшествующей ИП по `cstAgPn`, иначе 4; дубли cstAgPn в файле → разные схемы / ERROR (notes O1 §5.2).
4. UI шагов 1–2 обязателен; «в один клик» без превью несопоставленных — риск порчи DAG.
