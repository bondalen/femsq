## 1. Суть проблемы D1

В целевой модели один канонический **`Dbt`** может со временем проходить через **несколько** слотов **`invDbt`** (разные `iKey` / СФ) — красный мост `invDbtDbt` (P1, осцилляция документа основания).

**В выгрузке свода нет формального признака**, что две строки (два СФ / два потенциальных `invDbt`) — один и тот же `Dbt`.  
В **старой структуре БД** (`cnInvAccnt` / `cn_inv_dbt`) эта связь **не хранится**.

Связь 1:`Dbt` → N:`invDbt` восстанавливалась **вручную вне Access** при согласовании исходящих Excel `ags_Yr_DbtChangesRslt_*`.

---

## 2. Как это делалось в жизни (владелец, сегм. 24)

1. В Rslt у долга в **крайней** рассматриваемой выгрузке нет «продолжателя» → строка выглядит как **погашенная**.
2. Специалисты при согласовании: долг **не** погашен.
3. При разборе (чаще по **совпадающей сумме** + договор/контрагент) находится долг в крайней выгрузке на **другом СФ**.
4. В Excel Rslt: данные «нового» долга (в т.ч. № СФ — для этого в блок квартала добавили колонку СФ) **переносятся** в строку «старого»; строка «нового» **удаляется**.
5. Контроль: **совпадение общей суммы** долгов по выгрузке до/после правки.

Итог: единственное устойчивое место, где зафиксированы такие 1:N, — **файлы Rslt** (и красный фон / ручные правки в них), не таблицы FishEye.

## 4. Вывод для cutover / M2

| Утверждение | Статус |
|-------------|--------|
| Автоматический seed «1 `Dbt` = 1 слот по всем ~11907» **без учёта Excel** | **Неполон** для P1 |
| Признаки 1:N в `ags` / `cn_inv_dbt` | **Отсутствуют** (как правило) |
| Практический путь | Инвентаризация **Rslt Excel** → реестр связей 1:N → применить при seed `invDbtDbt` |
| Ценность DEV | Каждую найденную связь фиксировать в реестре ниже — облегчит prod |

**Стартовый seed-слой (гипотеза, уточняется):**

1. База: 1 `Dbt` на зерно S73 / слот `(idInv,idNum)` (**большинство**).  
2. Поверх: **мердж** слотов в один `Dbt` по реестру Excel-связей (и ручным находкам DEV).  
3. Без записи в реестре — **не** угадывать 1:N в ETL.

Это **не** отменяет модель «1 `Dbt` может иметь много слотов» — отменяет иллюзию, что БД сама знает эти связи.

### Сверка `ags_Yr_DbtChangesRslt_26-0212_26-0217.xlsx`

Лист: `ags_Yr_DbtChangesRslt_26-0212`. Колонки «Реквизиты документа…» по кварталам: **T** (2025.I), **AI** (2025.II), **AX** (2025.III), **BM** (блок около 2025.IV; у заголовка рядом ещё **BN** с тем же текстом — в данных пуста).

| Кол. | Непустых строк данных | Вывод |
|------|----------------------:|-------|
| **T** | 10 | те же L001–L010 (стр. **134–139**, **141–144**; **140** — `ciaName` 1 без T) |

**Каталог файлов для разбора (минимум):**

- `excel/2026_03/debit/ags_Yr_DbtChangesRslt_26-0505.xlsx` ← просмотрен по кол. **T** → L001–L010

Признаки-кандидаты при чтении Excel (не автомат, а подсказка): **непустая кол. «Реквизиты документа…»** с № **≠** левому `invNumEnumN` (и не «укорочение» того же номера, как BM=`732` vs `732 от …`); красный фон; «погашение» при живом долге у специалистов; одинаковая сумма на другом СФ того же договора.

### Сверка сумм в БД (`cnInvAccnt` / `cn_inv_dbt`) по cn 1466 / 1191

Метод: все `(ciaName, dbt_ttl)` на зонтиках **12032** / **12033** × точное совпадение `dbt_ttl` на **других** `inv` того же `cn`.

| Результат | Деталь |
|-----------|--------|
| Совпадений | **ровно 10** = L001–L010 (те же пары сумм → СФ `90/7/49/46/32/21` и `89/47/33/20`) |
| Новых кандидатов 1:N | **нет** |
| Одновременных выгрузок (сумма на зонтике и на близнеце в одном `uplStatusOnDate`) | **0** — смена СФ во времени, не дубль в одном срезе |

Слоты **без** близнеца по сумме на других СФ договора:

| Зонтик | `ciaName` | Суммы в истории | Замечание |
|--------|-----------|-----------------|-----------|
| 12032 | **1** | 108 063 847.03 → 4 151 101.82 (до 2023.I) | Ранний «ком» = L001–L006 + 4 151 101.82; затем остаток, похоже, ушёл в `ciaName` 2 |
| 12032 | **2** | 200 000 → **4 351 101.82** (жив до 2025.II) | 4 151 101.82+200 000; в Excel T пусто — **не** P1 |
| 12033 | **1** | 77 751 751.17 → **3 995 284.60** (жив до 2025.II) | Рядом с разбиением на L007–L010; в Excel T пусто (стр. 140 / аналог 91) — **не** P1 |

Итог: по этим двум договорам метод «сумма на другом СФ» в БД **не расширяет** реестр за пределы Excel T; «дыры» 1 и 2 — внутризонтичная нарезка (P2), не скрытый мост на другой `inv`.

## 6. Связь с D2 / M1

- **D2** (P1 после cutover в воронке) опирается на тот же механизм `invDbtDbt`, но уже **в БД**.  
- **D1 cutover** обязан **восстановить историю** из Excel, иначе Rslt/отчёты разъедутся с согласованной реальностью специалистов.
