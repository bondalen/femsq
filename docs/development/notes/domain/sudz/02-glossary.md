### ДЗ

Дебиторская задолженность.

### Общий свод ДЗ

Квартальная выгрузка из бухгалтерской системы о состоянии ДЗ на дату конца квартала.

- Содержит и **непросроченную**, и **просроченную** задолженность.
- Типовое имя файла: `Дт Задолженность на 3*.**.202* (Общий свод)*.xlsx`.
- **Не содержит** привязки к стройке (`cst` / `cstAgPn`) — для этого нужны файлы `export_{счётГК}` (см. ниже).
- Загружается в **FishEye.ags** через MS Access (шаг 1.1.1.1 процесса).
- Роль в процессе — см. [03-processes.md](./03-processes.md) (P1).

### Просроченная задолженность

ДЗ с истекшим сроком погашения на дату свода.

- В своде обычно видны колонки срока погашения и суммы просрочки.
- В модели данных **одна логическая задолженность** должна иметь стабильный идентификатор между выгрузками (см. [04-data-model §1.1](./04-data-model.md)) — сейчас это **не реализовано**.

### Сущность «Задолженность» (целевая)

Отдельная доменная сущность со **стабильным ID**, не сводимая к текущему счёту-фактуре или договору.

- На текущем уровне эксплуатации это **`cnInvAccnt`** (`ciaKey`); значение в выгрузке — **`cn_inv_dbt`**.
- Может **сменить** счёт-фактуру (`inv`) и следовать за сменой договора у `inv`.
- У одного `inv` в одной выгрузке может быть **несколько** задолженностей.
- Сопоставление новой строки свода = поиск уже существующего ID; при смене СФ текущий функционал **ломается** (пример Rslt 85 — [04-2](./04-2_example-rslt-82-85.md)).
- Параллельно есть недоделанный **`invDbt`**. Каталог описаний: [04-1_ms-descriptions.md](./04-1_ms-descriptions.md).

### Счёт-фактура (`inv`)

Документ `ags.inv`.

- Может **«гулять» между договорами** `cn` (поэтому связка через устаревший `cn_inv` недостаточна).
- Может **менять имя**.
- **Не** является стабильным ключом задолженности.

### `cn_inv` (устаревшая связка)

Старая жёсткая связка договор–счёт.

- Устарела для идентичности из‑за прогулок `inv` между договорами.
- Статус в модели: **legacy**.

### Строка выгрузки (`cn_inv_dbt`)

Значение задолженности **`cnInvAccnt`** внутри пакета `cn_inv_dbt_upl` (конкретная выгрузка общего свода).

- При стабильном СФ match обычно справляется (Rslt 82).
- При смене СФ — разрыв; в Rslt правят вручную по **сумме + номеру и дате договора** (Rslt 85, красный фон).

### `ciaName` (костыль)

Поле имени на карточке `cnInvAccnt` (и в диагностике дублей).

- Позволяет относить строки к **одной из нескольких** задолженностей одного счёта-фактуры (**P2**).
- Не решает смену СФ у той же задолженности (**P1**, S7).

### Осцилляция документа основания (P1)

Смена **объекта** в поле «Документ основания» у одной задолженности между выгрузками — не переименование одной СФ.

- Пример: **решение суда** `А19-16343/2021` ↔ **исходная СФ** `90` (долг 9527.42).
- У `90` в доступных сводах — **один** долг; у судебного номера — **несколько** (P2).
- Отдельно: **P5** — смена имени у того же объекта СФ.
- Реестр: [04-3](./04-3_problems-solutions.md). `invDbt` P1 **не** решает.

### Несколько долгов на один документ основания (P2)

В одной выгрузке у одного номера в «Документ основания» — несколько строк ДЗ. Часто это **решение суда** (пример свода 31.12.2025: **7** у `А19-16343/2021`, **5** у `А19-16352/2021`).

- Костыль: `ciaName`. Задумка: `invDbt.idNum` (не добита).
- Исходная СФ вроде `90` в проверенных сводах несёт **один** долг.

### `invDbt` / `invDbtValue`

Недоделанный слой «долг у счёта-фактуры» (`idInv`+`idNum`; value по выгрузке).

- Разовая заливка `invDbt` **2022-12-06**; `invDbtValue` с **2023-04** пуст.
- Крайняя структурная попытка: могла закрыть P2, не закрывает P1. См. [04-3 §2](./04-3_problems-solutions.md).

### PartyOrg / `cn_s_org_smpl`

Связь **сторона договора ↔ организация без дат**.

- Канон для привязки `export_*` / `cn_inv_pm` (дата договора в export отсутствует — **P7**).
- Dated-слой `cn_s_org` — история допсоглашений (**PartyOrgPeriod**), не обязателен для создания Debt.
- Проблема dual-FK на `cnInvAccnt`: **P6**. Целевой порядок: [04-3 §5](./04-3_problems-solutions.md).

### `Dbt` (целевая, эскиз владельца — уточнено в S14)

Канон задолженности в целевой модели: стабильный ID, **не** зависящий от документа основания.

- **Уточнено в S14:** FK на сторону **не нужен вовсе** (сильнее черновика S13) — сторона выводится через `Cn`→`cn_s`→`cn_s_org(_smpl)` или фиксируется как снимок на `DbtValue`. Допущение «1 сторона на роль на договор» подтверждено на всех 2329 договорах.
- Документ основания — снаружи, через мост **`invDbtDbt`** (M:N к `Inv`, `UNIQUE(inv, dbt)` — см. S16), а не в идентичности.
- Заменяет по смыслу `cnInvAccnt`/`cnInvAccntSmpl`; на неё перецепляются `cnInvCmm*`.
- Подробно: [04-3 §6](./04-3_problems-solutions.md#6-целевая-модель-судз-dbt--docbasis-многие-ко-многим-предложение-s13) (черновик S13) и [04-3 §7](./04-3_problems-solutions.md#7-ревизия-целевой-модели-по-эскизу-владельца-dbt--invdbtdbt--dbtvalue-s14) (эскиз владельца, S14, актуальный).

### `invDbtDbt` / `DbtValue` (целевая, эскиз владельца, S14)

Замена концепции `DbtDoc` из S13 именами и слоями владельца, опирающаяся на уже живые таблицы:

- **`invDbtDbt`** — мост **многие-ко-многим** между `Inv` и `Dbt`, с `UNIQUE(inv, dbt)` (уточнено в S16 по предложению владельца: долг может «гулять» по СФ, но не может гулять по «долгам от СФ» в пределах одного СФ). Поле `invDbt` (слот `idInv`+`idNum`) — обязательное уточняющее, а не часть ключа; отдельно `UNIQUE(invDbt)`. Один `Dbt` → много строк `(inv, dbt)` во времени (закрывает **P1**); один `Inv` → много `Dbt` через разные слоты (закрывает **P2**).
- **`DbtValue`** — факт-снимок по конкретной выгрузке: `Dbt` + `upl` + явные FK на `accnt`/`cnNum`/`cn_s_org` (а не текст) для полей, которые могут отличаться от выгрузки к выгрузке.
- Заменяет по смыслу `cn_inv_dbt`; **не** требует распознавания `doc_base` для целевого процесса (match идёт по сумме/договору/стороне), но `doc_base` полезен разово при точечной реконструкции истории уже загруженных строк.
- Оба — новые таблицы; `invDbt` как «слот» — существующая, но замороженная с 2022-12-06 таблица, требует оживления.

### `cnNum` (существующая, обнаружена заново в S14)

Историзированный номер **договора** — точный симметричный аналог `invNum`, но для `cn`. Создана **2022-01-11**, в тот же день, что `invNum`. 2354 строки на 2328 договоров, есть `cnNumType`.

- Ранее не учитывалась в реестре моделей СУДЗ; в целевой модели (S14) используется как источник поля «Договор» для `DbtValue`.

### `DocBasisName` (= `invNum`, уже существует)

Историзированное имя счёта-фактуры/документа основания (0..N на один `inv`).

- Механизм уже есть в БД как **`invNum`** (1:N к `inv`) — закрывает **P5** почти без нового кода.

### Непросроченная задолженность

ДЗ со сроком погашения не ранее даты свода.

- Присутствует в том же общем своде, но не является объектом «работы по просрочке» портфеля начала года.

### Портфель начала года

Множество просроченных задолженностей по своду на **31.12 предыдущего года**.

- Это объект работы СУДЗ в течение **текущего** календарного года.
- Источник: свод вида `… на 31.12.20YY`.

### Урегулирование

Исход, при котором позиция портфеля перестаёт быть открытой просрочкой для целей СУДЗ:

- погашение задолженности, **или**
- перенос срока погашения.

*(Как именно перенос отражается в следующем своде — уточняется, вопрос В10.)*

### Мероприятие по урегулированию

Действие или зафиксированный факт работы по долгу из портфеля начала года (претензия, переписка, переговоры и т.п.).

- Собирается от специалистов, ответственных за отдельные задолженности (шаг 1.1.2).
- Вносится в **FishEye.ags** через MS Access с контролем корректности (шаг 1.1.3).
- Пример материалов на шаре: кейс `26-0526_Головинова`.

### Внутригодовая новая просрочка

Задолженность, ставшая просроченной **в течение текущего года**.

- По ней работа СУДЗ в этом году **не** ведётся.
- В исходящие сведения года **не** включается.

### Сопоставленные (идентифицированные) задолженности

Записи ДЗ после загрузки и сопоставления в **FishEye.ags** (в т.ч. с привязкой к стройке), пригодные для работы специалистов.

- Отражаются в выгрузке `ags_Yr_DbtChangesRslt_*` нарастающим итогом с начала года до завершившегося квартала.

### ags_Yr_DbtChangesRslt

Промежуточный Excel-документ для оборота со специалистами.

- Имя: `ags_Yr_DbtChangesRslt_2*-****.xlsx`.
- Содержит сопоставленные задолженности **нарастающим итогом** с начала года до конца квартала.
- **Извлекается из FishEye.ags** через MS Access (не «сырой» файл бухучёта); Access-запрос обычно читает `ags_Yr_DbtChanges`.
- Специалисты заполняют сведения о мероприятиях; затем данные возвращаются в БД (шаги 1.1.1–1.1.3).

### ags_Yr_DbtChangesRsltD644 / «запросы 644»

Семейство Access-запросов / листов выгрузки для **итогового документа** филиала 644.

- Имя: `ags_Yr_DbtChangesRsltD644_*` (маркер **644** в наименовании).
- Строит приложение «Сведения о ходе работы…» из уже собранного Rslt: join к `ags_cstAgPn`, `ags_cn_inv_dbt`; мероприятия → колонка **«Комментарий Филиала 644»**.
- Нужны, потому что результат функций/процедур SQL Server **не до конца** оформлен как готовое приложение — финальная обработка в MS Access.
- История SQL: `femsq/debit/23-0421_sql.docx` (на шаре). См. [03-processes §1.2.4](./03-processes.md).

### Итоговый документ

Построчный исходящий Excel для заинтересованного подразделения (ежеквартально).

- Файл: `Приложение N. Сведения о ходе работы по балансовым счетам 606012, 762210, 767502.xlsx`.
- Счета в образцах: **606012**, **762210**, **767502**.
- Лист = результат запроса `ags_Yr_DbtChangesRsltD644_*`.
- Образцы: `excel/2025-12/debit/Приложение 2.…xlsx`, `excel/2026_03/debit/Приложение 1.…xlsx`.

### Итоговый сводный документ

Годовой агрегат просроченной ДЗ **в разрезе счетов бухгалтерского учёта**.

- Готовится **один раз в год** по итогам **4-го квартала**.
- Файл: `Приложение 1. Информация о состоянии дебиторской задолженности в разрезе счетов бухгалтерского учета.xlsx` (лист `СВОД по субсчетам Д644`).
- Направляется **совместно** с итоговым документом за Q4 (тогда свод — Приложение 1, построчный — Приложение 2).
- Образец: `excel/2025-12/debit/Приложение 1. Информация о состоянии…xlsx`.

### export_{счётГК}

Файл выгрузки по счёту главной книги (пример: `export_606012_26-0422.XLSX`).

- Даёт данные для **привязки задолженности к стройке** (`cst`, `cstAgPn`), которых нет в общем своде.
- Загружается в **FishEye.ags** через MS Access (шаг 1.1.1.2).
- Без этой привязки специалисты не могут вести работу по объектам.

### Привязка к стройке

Связь позиции задолженности с объектом строительства / САК.

- Сущности FEMSQ/Access: `cst`, `cstAgPn` (и связанный контур агента стройки).
- Источник для установления связи при квартальной загрузке — файлы `export_{счётГК}`.

### Исходящие сведения

Общее имя для пакета документов, направляемых в заинтересованное подразделение после согласования (шаги 1.2.*).

- На практике (S20) пакет включает **итоговый документ** (каждый квартал) и, по итогам года, ещё **итоговый сводный документ**.
- Готовится из **FishEye.ags** через MS Access (в т.ч. запросы `*D644*`).
- Образцы файлов есть на шаре (В9 закрыт по наличию примеров).

### Счёт ГК

Счёт главной книги — разрез общего свода (отдельные листы книги) и суффикс в именах `export_{счётГК}`.

- Примеры: `601300`, `606012`, `761010`, `762210`, `767501`, …
- В **итоговом документе** (образцы) фигурируют в основном `606012`, `762210`, `767502`.

### MS Access (в контуре СУДЗ)

Клиент к схеме **FishEye.ags** для оператора СУДЗ.

- Загрузка свода и `export_*`, выгрузка `ags_Yr_DbtChangesRslt`, внесение мероприятий, финальная сборка итогового / сводного документов (запросы `*D644*` и др.).
- Целевой аналог в FEMSQ — Java/UI поверх той же (или эволюционирующей) модели `ags`.
