## 1. Задача

Один канонический **`Dbt`** может иметь **несколько** слотов **`invDbt`** (на **разных** `iKey` / СФ) — осцилляция документа-основания (P1).

По умолчанию после C1: **1 новый слот → 1 новый `Dbt`**.  
Исключения (несколько `invDbt` → один `Dbt`) — **отдельная** предметная область, не путать с **КСДД** (несколько `invDbt` на **одном** `iKey`, P2).

**Суть P1 (владелец, 2026-08-31):** история multi-Dbt — про **отсутствие** того же `Dbt` в новой выгрузке относительно базовой, а не про уменьшение суммы. Если сумма уменьшилась, `Dbt` **идентифицирован** и в базе, и в текущей выгрузке — это другой класс событий.

## 2. Три пути обнаружения / склейки

| # | Путь | Контекст | Автоматизация | Полнота |
|---|------|----------|---------------|---------|
| **1** | **Исторический** (cross-iKey по сумме / следы Rslt) | Загрузка; diff base↔curr | Частично: F1 cross-iKey, реестр L* (D1/D2) | Частная |
| **2** | **Исчезновение + overdReduced** | Загрузка; `yr.cn_inv_dbt_upl` → curr | Очередь P1-кандидатов (C2); auto-merge — по опыту UI | Частная |
| **3** | **Жалоба специалиста** | Вне воронки | UI rebind (§3) | **Полная** |

**Принцип:** воронка 0069 — **частная** задача (пути 1–2). **Полный** объём multi-Dbt — **двунаправленный UI** (путь 3).

### Путь 1 — исторический

- Реестр **L001–L010** ([04-5](./04-5_dbt-invdbt-cardinality-d1.md)); эталон `dbtKey=85` → `12032` + `20505`.
- **D2:** тот же `Dbt` + новый слот при sum-match **на другом** `iKey`.
- C1 сегодня: F1 только **внутри** `iKey`.

### Путь 2 — исчезновение `Dbt` (не «уменьшение суммы»)

#### 2.1. Определение «исчезновения»

**Исчезнувший `Dbt`** (для портфеля base→curr):

- на **базовой выгрузке года** `ags.yr.cn_inv_dbt_upl` у `Dbt` есть **`DbtValue`** (через слот `invDbt`);
- на **текущей** выгрузке curr **нет** `DbtValue` на **том же** слоте `invDbt` (долг «выпал» из среза curr по прежнему якорю слота).

Это **не** случай «`dvTtl` уменьшилась, но Value на curr есть» — там `Dbt` по-прежнему идентифицирован.

Колонка Rslt **`_погашено`** / тех. **`overdReduced`** (`NULLIF(Overd_base − Overd_curr, 0)`) — **следствие** исчезновения или снятия просрочки для отчётности D644, **не** самостоятельный критерий P1.

#### 2.2. Sum-match для кандидатов

Для каждого **исчезнувшего** `Dbt` берём суммы из контекста исчезновения (в т.ч. **`overdReduced`** и/или `dvTtl` base, как согласуется с Rslt).

В **Tbl текущей** выгрузки ищем строки с **совпадающей полной суммой** `cidutDebt` (сегм. 12, ε=0.01).

- **Без** ограничения «тот же договор/контрагент»: прецеденты L* — один cn; в тяжёлом случае может смениться и это.
- Рассматриваем **все** совпадения сумм из пула «исчезнувших» → кандидаты P1 (часто другой `iKey`).

**Контр-кейс 82:** исчезновения **нет** (тот же СФ, Value на curr); `overdReduced` есть, но P1 не нужен.

#### 2.3. Базовая vs квартальная выгрузка (рекомендация)

| Режим | Base upl | Назначение | Приоритет |
|-------|----------|------------|-----------|
| **A (обязательный)** | **`yr.cn_inv_dbt_upl`** — базовая выгрузка **года** | Портфель просрочки года; итог **D644** / `ags_Yr_DbtChangesRsltD644_*`; отчётность о работе с долгами **из базы года** | **MVP пути 2** |
| **B (опционально)** | Предыдущий квартал в `yr_upl_p` (Q1→Q2…) | «Перфекционизм»: исчезновение между соседними кварталами | **Фаза 2**, если появятся кейсы |

**Контекст года (`yrKey`, 2026-08-31):** upl на **31.12.Y** штатно входит в **два** портфеля — IV-й квартал года **Y** и база года **Y+1**. Разрешение base для C2/воронки — **не** по `upl_key` alone, а по паре **`(uplKey, yrKey)`** контекста запуска:

```sql
SELECT y.cn_inv_dbt_upl FROM sudz.yr y
JOIN sudz.yr_upl_p yp ON yp.yr_upl_p_yr = y.yr_key AND yp.cn_inv_dbt_upl = @uplKey
WHERE y.yr_key = @yrKey
```

Пример **901**: в yr **900** → base **801**; в yr **901** → base **901** (self-base, diff не нужен — данные из Q4-загрузки).

**Рекомендация (2026-08-31):** реализовать **только режим A** в C2/очереди P1. Режим B — отложить: удвоение логики diff, риск шума, бизнес-процесс явно завязан на **базу года**, а `ags_Yr_DbtChangesRslt_*` — промежуточный сбор комментариев по этому портфелю. Режим B добавить, если при эксплуатации A всплывут регулярные Q↔Q кейсы без следов в базе года.

Связь с **C2** (`DbtValueLoad` / Exist) — естественное место в воронке.

### Путь 3 — UI специалиста (общий)

Обнаружение **любыми** способами вне ETL. **Rebind** `invDbt` → существующий `Dbt`; **cleanup** осиротевшего `Dbt` при необходимости.

- **UI A:** Договоры (0071): `cn` → СФ → `invDbt` → «Привязать к Dbt…»
- **UI B:** Экран **Dbt**: «Добавить слот…»

Не входит в чекбоксы 0069.

## 4. Именование: «погашено» vs `overdReduced`

### 4.1. Разделение слоёв (✅ утверждено 2026-08-31)

| Слой | Имя |
|------|-----|
| Excel Rslt / специалисты | колонка **`_погашено`** — **без изменений** |
| UI отчётов FEMSQ | **«Погашено»** (русский) |
| Код (Java/TS/GraphQL/CTE) | **`overdReduced`** |

Переименование `pogasheno` → `overdReduced` в коде — **отдельный** рефакторинг после C2; не блокер документации.

### 4.2. Смысл `overdReduced`

`NULLIF(Overd_base − Overd_curr, 0)` — уменьшение **просроченной** части между base и curr upl. Не путать с **`dvDateMaturity`** / `maturity` (дата срока).

Для P1: `overdReduced` — **входной сигнал sum-match** вместе с исчезнувшими `Dbt`, не замена критерия «исчезновения».
