## P1. Квартальный цикл работы с просроченной ДЗ

### Назначение

Ежеквартально подготовить документ **«Исходящие сведения»** для заинтересованного подразделения: текущее состояние просрочки по **портфелю начала года** и **мероприятия** по её урегулированию.

Клиент к БД **FishEye.ags** на текущем этапе — **MS Access** (загрузка, выгрузка, внесение мероприятий, контроль, согласование правок).

### Временная логика года Y

```text
31.12.(Y−1)  ──►  портфель начала года Y
                    (просроченные из свода на 31.12.(Y−1))

Q1 / Q2 / Q3 / Q4 года Y:
  общий свод + export_{счётГК} → FishEye.ags (Access)
  выгрузка ags_Yr_DbtChangesRslt → специалисты → мероприятия → FishEye.ags
  проект «Исходящие сведения» → согласование → финальная отправка
  (новая просрочка, возникшая в Y, в работу не берётся)

31.12.Y  ──►  портфель начала года (Y+1)
```

### Правила включения

- **Просрочена на 31.12.(Y−1)** — в работе года Y и в исходящих сведениях.
- **Стала просроченной в течение Y** — не в работе и не в исходящих сведениях.
- **Непросроченная на дату свода** — не объект «работы по просрочке» портфеля начала года.

### Роль свода 31.12

Свод на **31 декабря** года Y:

- как обычный квартальный — для проверки портфеля начала Y;
- **плюс** — определяет **портфель начала года (Y+1)**.

### Приоритет реализации (S24)

Разбор блокеров миграции истории ([04-3 §7.4.2](./04-3_problems-solutions.md#742-уточнение-блокера-несколько-smpl-s24-роль-не-помогает-помогает-org)) показал: оставшиеся ~473 карточки и ретро-`cnNum`/`invNum` **не решаются** текущими данными `ags` — нужны исторические Excel-своды, которых на шаре нет за 2023–2025.

**Принятое решение:** историю отложить; сейчас — реализация живого квартального процесса (дерево ниже, сегмент S3) на **уже доступных** Excel диапазона **Q4’2025 – Q2’2026** (`2025-12`, `2026_03`, `2026-06` — есть и начало годового портфеля, и два квартала подряд). К истории — вернуться отдельным этапом, когда появятся архивные своды или возникнет конкретная бизнес-потребность в ретро-точности.

### Обобщённое дерево работ (ежеквартально) — сегмент S3

#### 1. Подготовка документа «Исходящие сведения»

##### 1.1. Подготовка и оборот `ags_Yr_DbtChangesRslt_2*-****.xlsx`

Документ с **сопоставленными (идентифицированными)** задолженностями **с начала года до завершившегося квартала нарастающим итогом**.

- Предназначен для заполнения специалистами, ответственными за отдельные задолженности.
- Рассылается им; от них собирается информация о выполненных **мероприятиях** по урегулированию объектов **просроченной задолженности** из **портфеля начала года**.
- Канал сбора в Excel — колонки **«новый…»** (`cur_new` / `mery_new` / `cstAgPn_new` и аналоги); внесение и контроль — в ходе **1.1.2** (особенно **1.1.2.2**); веха готовности — **1.1.3**.

###### 1.1.1. Подготовка файла и рассылка

Выполняется через **FishEye.ags** клиентом **MS Access**:

- внесение данных из **общего свода ДЗ** в БД;
- извлечение из БД файла `ags_Yr_DbtChangesRslt_2*-****.xlsx`;

####### 1.1.1.1. Загрузка общего свода

Загрузка `Дт Задолженность на 3*.**.202* (Общий свод)*.xlsx` в **FishEye.ags** через MS Access  
(факт: пакет `cn_inv_dbt_upl` + строки `cn_inv_dbt`).

**Разрыв (S5):** после загрузки должен выполняться **match** строки к стабильной сущности «Задолженность»; функционал **не завершён** → костыли и ручная доработка Rslt. См. [04-data-model §1.1](./04-data-model.md).

**Форма-«ядро» шага и полный алгоритм — найдены и разобраны (S27/S29, закрывает A4/G3):**

- **Главная форма** `CnInvDbtUpl_2` — список выгрузок (`upl_date`, `upl_name`, `upl_key`) с вкладками «загрузка», «выгрузки платежей [ПлатРТ]», «счета, суммы», «задолженности, кратко», «задолженности, чтение».
- **Вложенная форма** `CnInvDbtUpl>File_f` — карточка конкретной выгрузки: поле пути к файлу (`cidufPath`), флаги **«Обновлять»** (`cidufFlLoad` — писать вставки в БД) / **«обнов. по исх?»** (`cidufFlTbl` — перечитать Excel в буфер `CnInvDbtUplTbl`), кнопка **«загрузка»** (`btnCidufLoad`), текстовое поле журнала хода загрузки (`cidufLoadingProgress`, **RTF**/HTML-лог). Подвкладки: ход / перечень листов (`CnInvDbtUplFileSh`) / повторяющиеся СФ (`InvDouble`). Скрины: [UI/assets/26-0811-cn-inv-dbt-upl](../../UI/assets/26-0811-cn-inv-dbt-upl/README.md).
- **`btnCidufLoad_Click()` — полный текст найден и разобран (S29).** Этап 1: колонки Excel-листа отыскиваются **по точному тексту заголовка**, не по позиции (`Range.Find`, `LookAt:=xlWhole`) — устойчиво к перестановке столбцов между периодами; обязательные заголовки: «Документ основания (счет-фактура)», «№ контрагента», «Контрагент», «Договор», «Дата договора», «Дата образования», «Срок погашения», «Всего сумма задолженности в рублях», «Просроченная задолженность в рублях» (плюс необязательные «ИНН» / «Документ основания (присвоение ГК)» / «Ссылка»); каждая непустая строка колонки-якоря копируется в буфер `CnInvDbtUplTbl`.
- Этап 2 — **воронка из 10 подпроцедур**, каждая проверяет свой уровень (договор → СФ → простая карточка → полная карточка → факт выгрузки): при однозначном совпадении новые записи **вставляются автоматически** (сохранённым запросом или построчно через DAO), при неоднозначности — только **показ в лог** для ручного разбора. Финальный шаг сверяет уже существующие в БД строки `cn_inv_dbt` с источником построчным diff по каждому полю (даты, суммы, документ, ссылка, № п/п).
- **Подформа `CnInvDbtUpl>File_f>InvDouble`** (существование подтверждено как факт, не гипотеза) — грид ручного разбора неоднозначных СФ/договоров, с кнопкой создания новой СФ+связи вручную, когда авто-сопоставление не проходит.
- Полный разбор воронки, точная формула сопоставления (`CiaNm.SumMatch`) и подтверждённые коды (`cn_s_type=2`=исполнитель) — [04-data-model §2.7](./04-data-model.md#27-полный-алгоритм-btncidufload_click--цепочка-сопоставления-подтверждено-s29). М9 (правило match) переформулировано точнее: [04-3 М9](./04-3_problems-solutions.md).
- `CnInvDbtUplFileSh` / `CnInvDbtUplTbl` / `CnInvDbtUplTblCnInv` / `CnInvDbtUplFileInvDouble` — локальные таблицы Access (не схема `ags`), структура и роль подтверждены.

####### 1.1.1.2. Загрузка привязки к стройке (`export_{счётГК}_*`)

Общий свод **не содержит** привязки задолженности к стройке (`cst`, `cstAgPn`).

Специалисты могут вести работу **только** в привязке к таким объектам, поэтому дополнительно в **FishEye.ags** через MS Access загружаются файлы вида `export_{счётГК}_*` — они позволяют **привязать задолженность** к стройке / САК.

####### 1.1.1.3. Выгрузка `ags_Yr_DbtChangesRslt`

Извлечение из **FishEye.ags** документа `ags_Yr_DbtChangesRslt_2*-****.xlsx` через MS Access.

В файле для специалистов — нарастающие срезы по кварталам **плюс** колонки для **ввода новых** сведений (в образцах: «Куратор / Мероприятия / Код стройки, **новый**, по состоянию на …»; техн. имена `cur_new` / `mery_new` / `cstAgPn_new`). Именно их заполняют на шагах **1.1.2.***. Маппинг полей: §1.2.6.

**FEMSQ:** такой Rslt **можно** формировать из данных приложения, если бэкенд отдаёт витрину портфеля (срезы + уже сохранённые куратор/мероприятия/код стройки из `yr.yr_CmmGr`) — см. §1.3. Процедура `Yr_DbtChanges` и хранение комментариев — [04-data-model §2.6](./04-data-model.md).

###### 1.1.2. Сбор сведений о мероприятиях

Сбор от специалистов информации о выполненных мероприятиях по урегулированию просрочки из портфеля начала года.

На практике специалисты заполняют в полученном Rslt колонки **«новый…»** (образец `…Rslt_26-0212…`: `cur_new`, `mery_new`, `cstAgPn_new`). Это **форма сбора** для **1.1.2.***. Аналог в файле `…Rslt_26-0505…` — три колонки «новый, по состоянию на май 2026».

В FEMSQ:

| Указатель на `yr` | Роль |
|-------------------|------|
| **`yr_CmmGr`** | Актуальная / «официальная» группа года: «старые» колонки Rslt; все исходящие, кроме Rslt повтор (D644, свод, Rslt сбор) |
| **`yr_CmmGr_New`** | Рабочая группа **новых** комментариев раунда (с **1.1.2.1**); используется **только** в **Rslt (повтор)** для колонок `*_new` |

Подробнее UI: [02-9 §1a Progress](../../UI/02-9_sudz-mvp-screens.md). Модель `cnInvCmm*` / групп: [04-data-model §2.6](./04-data-model.md) (S25).

####### 1.1.2.1. Получение первых результатов

После первичной рассылки **Rslt (сбор)** (шаг **1.1.1.3**: «старые» из `yr.yr_CmmGr`, колонки `*_new` **пустые**; `yr_CmmGr_New` не участвует) специалисты возвращают заполненные файлы.

Ответы **заливаются в БД** как черновик группы комментариев раунда. Группа связывается с годом через **`yr.yr_CmmGr_New`** (FEMSQ-расширение; в Access сейчас только `yr_CmmGr`). Это не свободный выбор «подгрупп специалистов» в UI запуска — один указатель года на рабочую группу новых.

Импорт возвращённых Excel в FEMSQ — **позже**; до тех пор черновик может вноситься вручную (экран «Долги / мероприятия» → группа `yr_CmmGr_New`) или иным согласованным способом.

####### 1.1.2.2. Циклические рассылки и сборы до качества

Пока качество ответов недостаточное:

1. **Формирование Rslt (повтор / контроль):**
   - «старые» ← `yr.yr_CmmGr`;
   - `*_new` ← `yr.yr_CmmGr_New`.
2. **Внесение и правка в БД** содержимого колонок `*_new` (и аналогов) в группу `yr_CmmGr_New` — через Access (история) / UI FEMSQ / будущий импорт Excel.
3. **Параллельный контроль корректности** ответов; при необходимости — снова п.1–2.

Подгруппы специалистов (если ведутся в Access) — внутренний путь консолидации в `cnInvCmmGr`; для FEMSQ MVP рабочая точка сбора — **`yr_CmmGr_New`**.

Когда качество устраивает — переход к вехе **1.1.3**, затем **1.2**.

###### 1.1.3. Актуальные данные специалистов в БД внесены

**Веха процесса** (решение владельца **S60**, 2026-08-09): оператор **прекращает вносить правки** в комментарии раунда. Отдельной операции FEMSQ «продвинуть New → `yr_CmmGr`» **не требуется**.

- После вехи готовят исходящие **1.2** (D644 / Свод): они читают комментарии из **`yr.yr_CmmGr`**. Актуальность этой группы к моменту выгрузки обеспечивает оператор (правка в группе `yr_CmmGr`, переназначение указателя года на нужную группу и т.п. — вне отдельной кнопки Progress).
- `yr_CmmGr_New` остаётся рабочей группой колонок `*_new` для **Rslt повтор** на время раунда сбора; обнуление/смена указателя — по необходимости до следующего раунда, не как обязательный шаг 1.1.3.

Хранение комментариев (`cnInvCmm*` + типы + группы) и разбор `Yr_DbtChanges` — [04-data-model §2.6](./04-data-model.md) (S25/S26). Свежесть dev-снимка относительно Excel-образцов — там же (М15).

##### 1.2. Окончательная подготовка исходящих документов

На практике итог для заинтересованного подразделения — не один абстрактный файл, а **письменные приложения** (сегмент **S20**). Готовятся через MS Access поверх данных FishEye.ags; Access-запросы делают **финальную** обработку того, что SQL Server (функции/процедуры) отдаёт ещё не в виде готового приложения.

**FEMSQ (S22–S23):** по результатам маппинга SQL↔Excel (§1.2.6) **есть возможность** строить такие же Excel из данных приложения при **корректной передаче** с бэкенда — см. §1.3. Access-дотягивание колонок/подписей в целевой архитектуре уходит в отчётный слой FEMSQ.

###### 1.2.5. Соответствие запросов `23-0421_sql.docx` ↔ Excel (S21)

**Правило цепочки** (повторяется каждый квартал):

1. Запрос **`ags_Yr_DbtChangesRslt_YY-MMDD`** читает **`ags_Yr_DbtChanges`** → сохраняется / выгружается как Excel для специалистов.

##### 1.3. Воспроизводимость Excel в FEMSQ (S22–S23)

По маппингу §1.2.6 и дереву §1:

| Документ дерева | Можно ли собрать из данных приложения при корректной отдаче бэкенда? | Условие |
|-----------------|---------------------------------------------------------------------|---------|
| **1.1** Rslt для специалистов | **Да** | Витрина портфеля (срезы до выбранной выгрузки) + «старые» из `yr_CmmGr`; `*_new`: **пустые** при Rslt (сбор); при Rslt (повтор) — из **`yr_CmmGr_New`** — см. §1.1.2 |
| **1.2** Итоговый документ (D644) | **Да** | ~18 полей с однозначным маппингом (§1.2.6 B); отбор просрочки портфеля; шапка письма — слой отчёта |
| **1.2** Итоговый сводный (год) | **Да** (отдельный отчёт) | Агрегат по счетам ГК — не тот же запрос, что D644 |

Оформление (длинные заголовки «по состоянию на…», «Приложение N к письму») — ответственность генератора Excel, не доменной модели. Качество строк (идентичность долга при смене СФ) — match/`Dbt`, не формат файла.

В целевой архитектуре FEMSQ финальная «доводка», которую сейчас делает Access поверх SQL Server (§1.2.4), выполняется **бэкендом / отчётным слоем** при передаче корректного набора полей.
