## P1. Квартальный цикл работы с просроченной ДЗ

### Назначение

Ежеквартально подготовить документ **«Исходящие сведения»** для заинтересованного подразделения: текущее состояние просрочки по **портфелю начала года** и **мероприятия** по её урегулированию.

Клиент к БД **FishEye.ags** на текущем этапе — **MS Access** (загрузка, выгрузка, внесение мероприятий, контроль, согласование правок).

### Временная логика года Y

```text
31.12.(Y−1)  ──►  портфель начала года Y
                    (просроченные из свода на 31.12.(Y−1))

Q1 / Q2 / Q3 / Q4 года Y:
  общий свод + export_{счётГК} → FishEye.ags (Access)
  выгрузка ags_Yr_DbtChangesRslt → специалисты → мероприятия → FishEye.ags
  проект «Исходящие сведения» → согласование → финальная отправка
  (новая просрочка, возникшая в Y, в работу не берётся)

31.12.Y  ──►  портфель начала года (Y+1)
```

### Правила включения

- **Просрочена на 31.12.(Y−1)** — в работе года Y и в исходящих сведениях.
- **Стала просроченной в течение Y** — не в работе и не в исходящих сведениях.
- **Непросроченная на дату свода** — не объект «работы по просрочке» портфеля начала года.

### Роль свода 31.12

Свод на **31 декабря** года Y:

- как обычный квартальный — для проверки портфеля начала Y;
- **плюс** — определяет **портфель начала года (Y+1)**.

### Обобщённое дерево работ (ежеквартально) — сегмент S3

#### 1. Подготовка документа «Исходящие сведения»

##### 1.1. Подготовка и оборот `ags_Yr_DbtChangesRslt_2*-****.xlsx`

Документ с **сопоставленными (идентифицированными)** задолженностями **с начала года до завершившегося квартала нарастающим итогом**.

- Предназначен для заполнения специалистами, ответственными за отдельные задолженности.
- Рассылается им; от них собирается информация о выполненных **мероприятиях** по урегулированию объектов **просроченной задолженности** из **портфеля начала года**.

###### 1.1.1. Подготовка файла и рассылка

Выполняется через **FishEye.ags** клиентом **MS Access**:

- внесение данных из **общего свода ДЗ** в БД;
- извлечение из БД файла `ags_Yr_DbtChangesRslt_2*-****.xlsx`;
- рассылка специалистам.

####### 1.1.1.1. Загрузка общего свода

Загрузка `Дт Задолженность на 3*.**.202* (Общий свод)*.xlsx` в **FishEye.ags** через MS Access  
(факт: пакет `cn_inv_dbt_upl` + строки `cn_inv_dbt`).

**Разрыв (S5):** после загрузки должен выполняться **match** строки к стабильной сущности «Задолженность»; функционал **не завершён** → костыли и ручная доработка Rslt. См. [04-data-model §1.1](./04-data-model.md).

####### 1.1.1.2. Загрузка привязки к стройке (`export_{счётГК}_*`)

Общий свод **не содержит** привязки задолженности к стройке (`cst`, `cstAgPn`).

Специалисты могут вести работу **только** в привязке к таким объектам, поэтому дополнительно в **FishEye.ags** через MS Access загружаются файлы вида `export_{счётГК}_*` — они позволяют **привязать задолженность** к стройке / САК.

####### 1.1.1.3. Выгрузка `ags_Yr_DbtChangesRslt`

Извлечение из **FishEye.ags** документа `ags_Yr_DbtChangesRslt_2*-****.xlsx` через MS Access.

###### 1.1.2. Сбор сведений о мероприятиях

Сбор от специалистов информации о выполненных мероприятиях по урегулированию просрочки из портфеля начала года.

###### 1.1.3. Внесение в БД

Внесение полученной информации в **FishEye.ags** через MS Access **с параллельным контролем корректности**.

##### 1.2. Окончательная подготовка исходящих документов

На практике итог для заинтересованного подразделения — не один абстрактный файл, а **письменные приложения** (сегмент **S20**). Готовятся через MS Access поверх данных FishEye.ags; Access-запросы делают **финальную** обработку того, что SQL Server (функции/процедуры) отдаёт ещё не в виде готового приложения.

###### 1.2.1. Проект документов

На основе данных после шага 1.1.3 готовятся:

1. **Итоговый документ** (ежеквартально) — построчные сведения о ходе работы по счетам **606012, 762210, 767502**.  
   Типовое имя файла:  
   `Приложение N. Сведения о ходе работы по балансовым счетам 606012, 762210, 767502.xlsx`  
   Лист Access/выгрузки: `ags_Yr_DbtChangesRsltD644_*` (маркер **644** в имени запроса).  
   Колонки (ознакомительно): счёт ГК, агент, контрагент (№/ИНН/имя), договор и дата, документ основания, даты образования/срока на 31.12 и на дату квартала, суммы всего/просрочки, погашено с начала года, код и наименование стройки, **«Комментарий Филиала 644»** (= мероприятия из Rslt).

2. **Итоговый сводный документ** (только по итогам **4-го квартала**, раз в год) — агрегат просрочки **в разрезе счетов бухгалтерского учёта**.  
   Типовое имя:  
   `Приложение 1. Информация о состоянии дебиторской задолженности в разрезе счетов бухгалтерского учета.xlsx`  
   Лист: `СВОД по субсчетам Д644`.  
   Направляется **совместно** с итоговым документом за Q4 (нумерация приложений: свод = Приложение 1, построчный = Приложение 2). В обычные Q1–Q3 сводного нет — построчный может быть «Приложение 1».

###### 1.2.2. Согласование разделов

- Рассылка проекта лицам, ответственным за разделы документа.
- Получение замечаний.
- Отражение замечаний в **FishEye.ags** через MS Access.
- Повторное извлечение откорректированных приложений.

###### 1.2.3. Направление итога

После согласования — направление приложений в заинтересованное подразделение (письмо филиала 644).

###### 1.2.4. Access SQL: цепочка Rslt → D644 (ознакомительно, S20)

Источник истории запросов: `femsq/debit/23-0421_sql.docx` (на шаре).

| Семейство запросов | Роль |
|--------------------|------|
| `ags_Yr_DbtChangesRslt_*` | Выборка из `ags_Yr_DbtChanges` → файл для специалистов (мероприятия), шаг 1.1 |
| `ags_Yr_DbtChangesRsltD644_*` | Преобразование Rslt в форму **итогового документа**: join к `ags_cstAgPn` (агент/стройка) и `ags_cn_inv_dbt`; поле мероприятий → «Комментарий Филиала 644» |

Зачем Access: данные с сервера **не до конца** доведены до вида приложения — нужна окончательная обработка в MS Access (переименование колонок, отбор счетов, подтягивание стройки/агента, оформление под письмо).
