## 1. Зачем костыль `ciaName`

В работе обнаружилось, что у одного документа основания (`inv`) в одной выгрузке может быть **больше одной** задолженности (**P2**). Быстрое решение — поле **`ciaName`** на карточке `cnInvAccnt`.

Если отбросить промежуточные звенья (карточки, smpl, org):

> **`(iKey, ciaName)` в старой структуре ≈ `(idInv, idNum)` в новой**  
> (для именованных: seed/`invDbtTmpCiaRel` уже ставили `idNum = TRY_CAST(ciaName AS int)`).

`ciaKey` — PK **карточки-костыля** (куда пишут `cn_inv_dbt` / cmm), **не** доказанное зерно долга.  
Колонка `ciaName` в целевую схему **не** переносится (S33); роль дискриминатора на СФ — **`invDbt.idNum`**.

## 3. Нужен ли `account_num` (СГК) в ключе?

### 3.1. Именованные

`named` тройка Rslt = `named` пара `(iKey, name)` = **141**.  
**СГК в ключе для named избыточен.**

### 3.2. Критерий «брожения» vs «разные долги»

Гипотеза владельца: долг может висеть несколько кварталов на одном СГК («надёжные»), затем перейти на другой («безнадёжные») и позже исчезнуть.

**Критерий:**

- если одно зерно `(iKey, ciaNameNull)` встречается под **разными СГК в одной и той же выгрузке** → это **разные** долги, СГК — часть ключа;
- если разные СГК **никогда не встречаются в одной выгрузке** → допустимо **брожение** (СГК — атрибут снимка).

**Факт по всему архиву `cn_inv_dbt`:**

| Метрика | Значение |
|---------|----------:|
| Пары grain×upl | ~42 354 |
| Из них с `n_acc > 1` в одной upl | **0** |
| Зёрна с >1 СГК за всю историю | **31** |
| Из них когда‑либо concurrent | **0** |

Печальный сценарий «два долга, СГК обязателен в ключе как дискриминатор одновременности» **на данных не подтвердился**.

### 3.3. Печаль оператора (единство всё равно не автоматическое)

«Никогда не в одной выгрузке» **≠** «это один долг». Нужна траектория сумм (или решение оператора).

Из **31** мульти-СГК:

| Класс | N | Правило |
|-------|--:|---------|
| Одна и та же `dbt_ttl` на двух СГК | **18** | один долг (переклассификация) |
| Нет общей суммы; при смене СГК ratio ∈ **[0.5; 1]** | **3** | скорее один (в т.ч. страховая амортизация **19769**, **80093**, **508**) |
| Скачок порядка величины (ratio ≫ 1 или ≪ 0.05) | **9** | скорее **два** долга под одним `Null` |
| Кратность **0.25** (ровно ¼) | **1** (`iKey=4480`) | спорный — только вручную |

**iKey на ручное рассмотрение (10 = 9+1)** — очередь **после seed** (решение **D5**, 2026-08-27); SoT перечня также: [cutover §1.2](../../../deployment/db-upgrade-sudz-invdbt-cutover.md#12-очередь-ручного-разбора-после-seed-d5--10-ikey).

- **Сплит (9):** `336`, `4786`, `6766`, `6770`, `6776`, `6798`, `6801`, `6812`, `6814`  
  (типично: мелкий хвост на `767502`, затем крупная сумма на `606012`).
- **Спорный (1):** `4480` (472 257 800 → 118 064 450 = ¼).

Seed: энтропия вверх (отдельные `Dbt`). Ручной разбор: подтвердить сплит или смержить; исход — в журнал / эту таблицу.

Эталон «один долг при смене СГК»: **19769** — после перехода `767502`→`606012` сумма только плавно снижается по выгрузкам.

## 4. Сколько точно долгов в старой структуре?

Рабочее зерно (канон S73):

**`(iKey, ciaNameNull)` ↔ слот `(idInv, idNum)`**,  
СГК — атрибут варианта/снимка (`invDbtVar` / факт), не часть ключа идентичности.

Формула на текущем срезе:

```
11 897  — база GROUP BY (iKey, ciaNameNull)
+     9  — сплит 9 зёрен «скачок порядка» → два долга вместо одного
±     1  — решение по iKey=4480 (один или два)
───────
11 906 … 11 907
```

| Утверждение | Число |
|-------------|------:|
| **Рабочая оценка числа долгов (после эвристического сплита 9)** | **11 906** |
| Если оператор решит, что `4480` — два долга | **11 907** |
| Диапазон до закрытия 10 ручных кейсов | **11 906–11 907** |
| Ручных кейсов | **10** (9 сплитов + 1 спорный) |

Не путать с:

- **12 693** — карточки `ciaKey`;
- **11 928** — строки Rslt-тройки (СГК в ключе; для seed слотов **не** канон).

Пересчёт обязателен на более свежем бэкапе `ags` (см. S26: dev отстаёт от последних Excel).

## 5. `invDbtTmpCiaRel` — след прошлой попытки

| Метрика | Значение |
|---------|----------:|
| Строк / distinct `cia` | **6366 / 6366** → **1 cia → 1 строка моста** |
| Distinct слотов `(idInv, idNum)` | **5995** |
| Слотов с несколькими cia | **354** → **много карточек → один слот** |
| Cia в двух слотах | **0** |
| Named: `idNum = CAST(ciaName AS int)` | **124 / 124** числовых имён (ещё 8 нечисловых) |

Схлопывание 354 слотов в основном: **то же имя + тот же счёт**, разные `ciaCn_s_org` (333); реже то же имя + разные счета (20).

Паттерн для `sudz`: мост **`invDbt` ↔ `ciaKey`(и)** с `UNIQUE(ciaKey)`, а не колонка `ciaName` на слоте.  
Seed: **`idNum ← ciaName`** для named.

6. **Следствия для FEMSQ (сегм. 22 / воронка)**

1. Create/Link на экране двоящих: кандидат old = `(iKey, ciaName/idNum)`; сумма±история; СГК — для Var/проверки, не для UNIQUE слота.
2. Автомат seed unnamed: мульти-СГК + плавный ratio → один слот; скачок порядка → **не сливать** (очередь оператору / два `idNum`).
3. UI: для спорных — лента `upl → СГК → сумма`.
4. Не возвращать `ciaName` как колонку целевого `invDbt` (S33); смысл — в `idNum`.
5. **Cutover prod:** однократный seed слотов по этому канону — [db-upgrade-sudz-invdbt-cutover.md](../../../deployment/db-upgrade-sudz-invdbt-cutover.md); планировочное N при энтропии вверх = **11 907**.
