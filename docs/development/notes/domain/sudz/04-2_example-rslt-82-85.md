Роли на текущем уровне эксплуатации: **`cnInvAccnt` = задолженность**; **`cn_inv_dbt` = значение этой задолженности в конкретной выгрузке** — этого недостаточно, когда меняется счёт-фактура.

---

## Роли таблиц (уточнение владельца, S7)

- **`cnInvAccnt`** — задолженность (сущность на текущем уровне эксплуатации).
- **`cn_inv_dbt`** — значение задолженности **в конкретной выгрузке** (`cn_inv_dbt_upl`).
- Функционала **не хватает**, когда в новой выгрузке у той же задолженности меняется документ основания (СФ): автоматический match ломается; в Rslt правят **вручную** (часто по **сумме**). Строки с красным фоном в Rslt — такие случаи.

---

## Строка 82 Rslt — обычный случай (СФ не меняется)

Покрывается текущим функционалом.

| | IV.2025 | I.2026 |
|--|---------|--------|
| Счёт ГК | 606012 | 606012 |
| СФ (док. основания) | **7947** | **7947** (без смены) |

| Контрагент | Газстройпром | то же |

| Код стройки | 051-2001061 | 051-2001061 |

В Rslt слева `invNumEnumN` = `7947`; колонка СФ I квартала пуста — смены документа нет.

**31.03.2026**, лист `606012`, строка **668**:

- СФ = `7947` (**тот же**), сумма = `70525000.01`, срок **46691**, просрочка = **0**.

Итог: одна и та же позиция узнаётся по СФ (+ контекст); изменение — **перенос срока** / снятие просрочки, не смена документа.

## Строка 85 Rslt — смена объекта документа основания (ручной match)

В I квартале в поле «Документ основания» приходит **другой объект**: не переименование СФ, а переход между **решением суда** и **исходной СФ**. Сопоставление с задолженностью IV квартала сделано **вручную** (по **сумме**, **номеру и дате договора**) и отражено в Rslt. Аналогично другие строки с **красным фоном**.

| | IV.2025 | I.2026 |
|--|---------|--------|
| Счёт ГК | 762210 | 762210 |
| Документ основания | **А19-16343/2021** (решение суда) | **90** (исходная СФ) |
| уточнение основания | 3 | (та же ветка множественности) |
| Договор | 32-425/05-18 | 32-425/05-18 |
| № контрагента / ИНН | 1241705 / 5407963646 | то же |
| Контрагент | ВМК, ООО | то же |
| Общая / просроченная | **9527.42** / 9527.42 | **9527.42** / 9527.42 |
| iKey (служебно) | 12032 | 12032 |

В Rslt слева остаётся `А19-16343/2021`, в колонке документа I квартала — `90` (результат ручной правки).

### Записи в общих сводах

**31.12.2025**, лист `762210`, строка **54**:

- СФ = `А19-16343/2021`, сумма = `9527.42`, договор `32-425/05-18`, контрагент 1241705, срок/даты 44788.

**31.03.2026**, лист `762210`, строка **63**:

- СФ = **`90`** (исходная СФ, не решение суда), сумма = **`9527.42`** (та же), тот же договор и контрагент, дата образования 44788.

Итог: без стабильного ID задолженности автоматика, завязанная на документ основания, **не** свяжет эти две строки свода; связь восстановлена человеком по сумме (и контексту договора/контрагента).

|---------|----------------------|-------------------|----------------|--------|
| 2024.IV | 7947 (слева) | 70 525 000.01 / та же | 45595 (2024-10-30) | 11002 |
| 2025.I | *(пусто = без смены)* | та же / та же | 45595 | 11002 |
| 2025.II | пусто | та же | 45595 | 11002 |

### Долг «85» — строка Excel **134**

Идентичность слева: `iKey=12032`, СФ **`А19-16343/2021`**, `уточнение основания=3`, договор `32-425/05-18` / `43243`, сумма **9527.42**.

| Квартал | СФ в колонке квартала | Сумма / просрочка | ciaKey квартала |
|---------|----------------------|-------------------|-----------------|
| 2024.IV | А19-16343/2021 (слева) | 9527.42 / 9527.42 | **15175** |
| 2025.I | **`90`** | 9527.42 / 9527.42 | **12505** |
| 2025.II | **`90`** | 9527.42 / 9527.42 | **12505** |
| 2025.III | **`90`** | 9527.42 / 9527.42 | **12505** |
| 2025.IV | *(пусто)* | 9527.42 / 9527.42 | **15175** |

**Итог 2025:**

- Смена СФ **`А19-16343/2021` → `90` произошла уже в 2025.I** (не впервые в 2026.I) и держалась в колонках I–III.
- При этом **`ciaKey` прыгал**: 15175 (А19) ↔ **12505** (при СФ `90`) — признак, что система заводила/цепляла **другую** карточку `cnInvAccnt`, а не стабильно вела одну сущность.
- В 2025.IV в Rslt снова `ciaKey=15175`, колонка СФ квартала пуста; в своде **31.12.2025** эта сумма снова как СФ **`А19-16343/2021`**.
- В своде **31.03.2026** снова СФ **`90`**; в Rslt 2026 стр. 85 снова ручная связка (слева А19, в 2026.I — `90`).

То есть «красная» проблема 2026.I — **повтор** уже случавшейся в 2025 смены имени СФ у той же суммы/договора, а не единичный сбой.

Соседние строки 133–139 того же `iKey=12032` / договора — другие суммы с другими `уточнение основания` и своими сменами СФ (7, 49, 46, …) — тот же класс множественности долгов на одном «старом» СФ.

Подтверждение владельца (S9): выгрузки **бессистемно** для одного и того же долга 85 возвращают то `А19-16343/2021`, то `90`.

### Долг «82»

Лист `606012`, строка **751** (в этом файле у листа иной порядок колонок / первая строка — данные):

- СФ = **`7947`** (стабилен)
- договор `1-306-12`, контрагент 1255867 / АО ГАЗСТРОЙПРОМ
- сумма **70 525 000.01**, просрочка **0**, срок погашения **46691** (как в 31.03.2026)

**Итог:** без сюрпризов — та же задолженность, СФ не скачет.

### Долг «85»

Лист `762210`, строка **54**:

- СФ = **`90`** (не `А19-16343/2021`)
- договор `32-425/05-18`, контрагент 1241705 / ООО ВМК
- сумма / просрочка **9527.42**, даты 44788
- «присвоение ГК» = `14`

Отдельной строки с суммой **9527.42** и СФ **`А19-16343/2021`** в этом своде **нет**.  
Строка с `А19-16343/2021` на том же договоре есть (напр. row 55), но это **другая** сумма (4 351 101.82) — соседний долг того же кластера, не «85».

**Итог:** на 30.06.2026 выгрузка снова отдаёт долг 85 как СФ **`90`**. Вместе с историей 2025–2026.I это выглядит так:

```text
СФ для одной и той же задолженности 9527.42 / 32-425/05-18 / 43243:

2024.IV свод/Rslt     А19-16343/2021
2025.I–III Rslt       90          (уже ручная/отражённая смена)
2025.IV свод 31.12    А19-16343/2021   ← снова А19
2026.I  свод 31.03    90
2026.II свод 30.06    90
```

То есть в бухгалтерской выгрузке меняется **объект** документа основания (решение суда ↔ исходная СФ), а не «переименовывается» одна СФ; сумма + договор + дата договора остаются опорой идентичности. Уточнение P1: [04-3](./04-3_problems-solutions.md).

## Вывод для модели

1. Пара **`cnInvAccnt` + `cn_inv_dbt`** достаточна, когда документ основания **стабилен** между выгрузками (пример 82), включая сценарий переноса срока.
2. При **смене объекта документа** (P1; пример 85: `А19-16343/2021` = решение суда ↔ `90` = исходная СФ) нужен match к сущности задолженности **не через текущий `inv`**, а через стабильный ID и/или согласованные правила. На практике ручное сопоставление опиралось как минимум на:

   - **сумму** задолженности;
   - **номер договора**;
   - **дату договора**;

   плюс очевидный контекст (счёт ГК, контрагент). Затем в Rslt вручную проставляется актуальный документ. Без учёта договора/даты одна только сумма недостаточна (на одном контрагенте/судебном зонтике бывают разные суммы и несколько долгов).

3. На одном судебном номере (`А19-16343/2021`) в своде 31.12.2025 — **семь** задолженностей с разными суммами; в Rslt — `уточнение основания` (2,3,4,5…) — аргумент за сущность задолженности + различение (**P2**), а не «один документ = один долг». Исходная СФ `90` в сводах 31.03/30.06.2026 несёт **только** 9527.42.

4. Смена объекта документа в **исходных** сводах (не только ошибка Rslt) — сильный аргумент, что поле «Документ основания» в выгрузке — **изменчивый атрибут**, а не ключ сущности.
