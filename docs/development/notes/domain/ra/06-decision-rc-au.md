## 1. Решение

Принять **вариант A**: логическое изменение в `ags.ra_change` + таблица представлений **`ags.ra_change_au`** (имя рабочее; уточнить в DDL-пакете 1.4.3) по образцу `ralpRaAu`.

| Отклонено | Почему |
|-----------|--------|
| **B** (расширить UX на `ra_change`) | Ломает смысл № изм.; опасно для Access/JAR 156 |
| **D** (dedupe/skip) | Против бизнес-требования истории представлений |
| **C** | Не нужен при проходимости A |

Подвариант сумм: **A1** (сумма / `fdKey` на Au) — целевой; миграция с `ra_change_summ` — в 1.4.3.

## 2. Инварианты переходного периода (из 1.4.2.3)

1. UX `ЗаПериодЗаОтчётОдинНомер` на `ra_change` **сохранить**.  
2. DDL только **additive** (+ миграция 1 Au на существующий `rac_key`).  
3. Поля рассмотрения на `ra_change` — **зеркало** актуального Au для Access / `RRcTimeList` / 156.  
4. Развёртка N Au в `RRcTimeList` / освоении — **не** обязательна для PASS apply type=5; полное включение в расчёт — отдельный шаг после cutover или только `_2606`-путь (вне пакета `_2605`).  
5. Параллельный type=5 из двух экземпляров — запрещён.

---

## 3. Критерий приёмки type=5 (для 1.4.3 / PASS §1)

На стенде `FishEye_prod_noM6` (или актуальной копии), файл `excel/2026-1119` свод ОА, JAR кандидата:

| # | Проверка | Ожидание |
|---|----------|----------|
| 1 | Dry-run type=5 | COMPLETED без фатала; RC NEW учитывает multi-строки |
| 2 | Apply type=5 | **без** 2601 на `ЗаПериодЗаОтчётОдинНомер` |
| 3 | Пара Excel-строк с одним № изм. и разными письмами (напр. ряды ~12068/13073) | один `rac_key`, **≥2** строки `ra_change_au` |
| 4 | Повторный apply (идемпотентность) | не плодит лишние Au; зеркало согласовано |
| 5 | UX на `ra_change` | по-прежнему уникален по `(period, rac_ra, rac_num)` |
| 6 | Старые потребители | `RRcTimeList` / чтение Access-ключей не требуют смены UX |

Дополнительно (качество, не блокер модели): статус аудита при ошибке файла не должен маскироваться как успешный COMPLETED без FAIL в логе — хвост отдельно.
