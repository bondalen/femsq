## 1. Вариант A — Au-подобно (эталон РАЛП)

### Идея

Разделить **логическое изменение** и **представление**:

| Уровень | Таблица (рабочее имя) | Зерно | Содержимое |
|---------|----------------------|-------|------------|
| Логическое изм. | `ags.ra_change` (как сейчас) | UX `(ra_period, rac_ra, rac_num)` **оставить** | № изм., дата изм., связь с базой; без «текущего» письма как единственного |
| Представление | **`ags.ra_change_au`** (новое; имя уточнить в 1.4.2.4) | UX **`(racAu_rac, racAu_arrived)`** по аналогии с `(ralpraRa, ralpraArrived)` | arrived/sent/returned + даты; сумма **или** FK на версию сумм / `fdKey` |

Плоский вход для расчёта (как `ags.ralp`):

```text
VIEW ags.ra_change_pres  ≈  ra_change  ⋈  ra_change_au
  → одна строка = одно представление
```

`RRcTimeList` (ветка изм.) и/или `fnMasteringRa*` читают развёртку → каждое представление участвует в сумме/статусе **отдельно** (паттерн §03).

### Что делать с `ra_change_summ`

Два подварианта (выбор в 1.4.2.4 / реализации):

| | A1: сумма на Au | A2: summ остаётся на `rac_key` |
|--|-----------------|--------------------------------|
| Плюс | Полная аналогия РАЛП (`ralpraCostAndVat` на Au) | Меньше миграции существующих 47 multi-sum |
| Минус | Миграция/двойная запись summ↔Au | Несколько представлений с **разными** суммами на одном `rac_key` снова требуют правила «чья сумма» |

Для блокера Excel (разные письма, часто близкие суммы) достаточно **A1 или A2 с суммой на представлении**; A2 «только latest на change» **не** закрывает K1, если суммы тоже различаются между строками файла.

**Рекомендация скетча:** стремиться к **A1** (сумма/fdKey на Au); существующие `ra_change_summ` — миграция «одна Au на change = текущий latest» либо deprecated после cutover (деталь реализации).

### Reconcile type=5

1. Resolve база → `ra_key` (как сейчас).  
2. Resolve/insert **`ra_change`** по `(period, ra_key, № изм.)` — одна логическая запись.  
3. Resolve/insert **`ra_change_au`** по `(rac_key, rainArrived|нормализованное письмо)` — как `RalpReconcileService` для Au.  
4. Коллизия двух Excel-строк с одним № изм. и **разными** arrived → две Au, **без** 2601 на `ra_change`.  
5. Одинаковый arrived → update той же Au (идемпотентность).

### Потребители

| Объект | Изменение |
|--------|-----------|
| DDL | новая таблица + UX; опционально VIEW |
| `AllAgentsReconcileService` | RC apply/match как RALP Au |
| `RRcTimeList` | FROM развёртки вместо «change + latest summ only» |
| `fnMasteringRa*_2606` | носитель = ключ Au (как `ralpraKey`) |
| `_2605` | **не трогаем** пакет; побочный эффект только через общий `RRcTimeList` (учесть в 1.4.2.3) |
| JAR 156 | не знает новую таблицу → **1.4.2.3** (nullable/additive DDL обычно безопасен, если 156 не пишет Au) |

### Плюсы / минусы A

| + | − |
|---|---|
| Закрывает K1–K3 | DDL + миграция + правка reconcile и 1–2 SQL-потребителей |
| Прямой образец кода (type=3) | Имя/миграция summ (A1 vs A2) |
| UX на логическом изм. можно сохранить | Совместимость 156 — отдельная проверка |

## 2. Вариант B — расширить зерно UX на `ra_change`

### Идея

Оставить одну таблицу; изменить unique, например:

- `(ra_period, rac_ra, rac_num, ra_arrived)` или  
- `(ra_period, rac_ra, rac_num, raс_date)` или  
- суррогат строки Excel  

Каждая Excel-строка «ОА изм» → **отдельный** `rac_key`.

### Следствия

| Тема | Оценка |
|------|--------|
| K1 история писем | формально да (каждая строка — свой arrived) |
| Смысл «Изм. № 2» | размывается: N строк с одним № — это N «логических» изменений для UI/отчётов |
| `ra_change_summ` | по-прежнему на `rac_key`; ок |
| `RRcTimeList` / mastering | начнут суммировать N строк с одним № без группировки «логическое изм.» — возможно **завышение**, если бизнес ждал одно изменение |
| Access / существующие запросы | ломают ожидание UX `ЗаПериодЗаОтчётОдинНомер` |
| Аналогия РАЛП | **нет** (у РАЛП № отчёта один, Au — дочерние) |
| 156 | смена UX на общей БД = **высокий** риск для действующего экземпляра |

### Плюсы / минусы B

| + | − |
|---|---|
| Нет новой таблицы | Ломает доменный смысл номера изменения |
| Проще DDL «в лоб» | Плохо для K3–K5; риск двойного счёта в освоении |
| | Не отвечает чисто на «письмо = представление при одном №» |

**Вердикт скетча по B:** допустим только как аварийный, если A принципиально блокирован совместимостью; **не фаворит**.
