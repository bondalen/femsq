## 1. Кто что пишет на проде сегодня

| Клиент | Type 5 (ОА / ОА изм) | Type 3 (РАЛП) |
|--------|----------------------|---------------|
| **JAR 156** | редко; модель только `ra` / `ra_change` / `*_summ` | основной писатель FEMSQ |
| **Access** | основной контур type 5 (`AuditRcCreateNew` / `ra_ImpNewQuRc`) | устаревающий |
| **Кандидат R1.0** | целевой писатель multi-presentation | уже умеет Au |

Access join RC: `(rcPeriod, ra_key, rac_num)` → `ags_ra_change` + `ags_ra_chSmLt` (latest sum).  
UX **`ЗаПериодЗаОтчётОдинНомер`** — контракт Access и 156; **не снимать** и **не расширять**, пока они на общей БД.

Потребители чтения (общие): `RRcTimeList`, `ra_chSmLt`, `fnMastering*Ra*`, `TimeRsltCAP` / `_2408` / `_2605` / `_2606` — все завязаны на **одну** строку change + latest sum.

## 2. Правило DDL на общей FishEye

| Действие | Допустимо при 156+Access? |
|----------|---------------------------|
| `CREATE TABLE ags.ra_change_au` (+ PK/UX, FK → `ra_change`) | ✅ **additive** — старый код таблицу не трогает |
| Миграция: 1 Au на каждый существующий `rac_key` из текущих arrived/sent/… + привязка к latest summ/fdKey | ✅ данные только читаются старым кодом из `ra_change` |
| Триггер / приложение: держать на `ra_change` **зеркало** «актуального» представления (поля arrived/sent/…) | ✅ Access/`RRcTimeList`/156 продолжают видеть привычную 1:1 картину |
| `DROP` / изменение UX `ЗаПериодЗаОтчётОдинНомер` | ❌ пока 156/Access пишут RC |
| Переписать `RRcTimeList` на развёртку N Au **сразу** | ⚠️ риск: Access/`_2605` начнут суммировать иначе без смены их кода — **отложить** до cutover или делать за флагом/новым VIEW |
| Новый VIEW `ra_change_pres` (change⋈Au) только для кандидата / `_2606` | ✅ не ломает старых потребителей |

**Аналогия:** `ralpRaAu` уже additive относительно «головы» отчёта; расчёт смотрит `ags.ralp`. Для RC на переходный период — **зеркало на `ra_change`**, полная развёртка в освоении — после вывода 156 или отдельным согласованным шагом VIEW.

## 3. Поведение писателей в переходный период

```text
                    ┌─ Access / JAR 156 ──► INSERT/UPDATE ra_change (+ summ)
                    │                      (Au не знают)
 FishEye (общая) ───┤
                    └─ Кандидат (A) ──────► ra_change (логический, UX прежний)
                                           + ra_change_au (N представлений)
                                           + UPDATE зеркала на ra_change
                                             (= выбранное «текущее» Au, правило ниже)
```

**Правило зеркала (черновик для 1.4.3):** на `ra_change` копировать поля рассмотрения с Au с максимальной `arrived_date` (или последней вставленной) — как «текущий статус» для Access и `RRcTimeList`.  
Несколько Au с разными письмами в БД есть; старый контур видит одно актуальное.

**Риск:** Access apply после кандидата может **перезаписать зеркало** и не создать Au → кандидат при следующем apply type=5 должен **восстановить Au** из Excel (reconcile idempotent), не полагаться только на зеркало.

**Параллельный apply type=5** из Access и кандидата — уже запрещён правилом двух экземпляров (один `af_type` за раз).

---

## 4. JAR 156

- Код 156 **не ссылается** на несуществующую `ra_change_au` → additive DDL его не роняет.  
- Type 5 в 156 редкий; при apply он останется в старой модели (1 change = 1 представление) — UX по-прежнему блокирует multi в **его** apply; это приемлемо до вывода 156.  
- Type 3/6 на 156 не затрагиваются.

---

## 5. Access / `_2605`

- Пока `RRcTimeList` и колонки на `ra_change` сохранены как сейчас — **поведение освоения для RC не меняется** (одно представление на изменение в отчёте).  
- Доработку `_2605` **не планируем** (см. [03](./03-ralp-mastering-vs-rc.md)).  
- Полный учёт N представлений в освоении — через обновление общих VIEW **после** cutover или только в `_2606`-пути на кандидате (решение в реализации 1.4.3; не блокер выбора модели A).

## 6. Вердикт 1.4.2.3

| Вопрос | Ответ |
|--------|-------|
| Блокирует ли совместимость вариант A? | **Нет** |
| Условие безопасности | additive DDL + **не** трогать UX `ЗаПериод…` + зеркало на `ra_change` + не форсировать развёртку в `RRcTimeList` до cutover |
| B (смена UX) | **отклонён** и с точки зрения двух экземпляров (слом Access/156) |

→ Можно фиксировать решение **A** в 1.4.2.4.

## 7. Пересмотр 2026-11-20

Вердикт §6 верен для **структуры** (аддитивная DDL не ломает 156/Access/`_2605`, откат таблицы — минуты). Для **данных** переходный период «кандидат + Access на type=5» неприемлем: два писателя одних изменений, зеркало перетирается, модели сумм расходятся (одно рассмотрение против N), записи кандидата в `ra`/`ra_change`/`*_summ` скриптом не откатываются. Решение: на прод — только переключение R1 (см. [06 §5](./06-decision-rc-au.md)); §3 этого документа применим лишь к окну переключения.
