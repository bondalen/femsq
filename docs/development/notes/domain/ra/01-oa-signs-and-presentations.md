## 1. Excel-признаки ↔ домен

Источник строк type=5: свод `*Свод*ОА*.xlsm`, лист отбора по whitelist `ags.ra_sheet_conf` (`ОА;ОА изм;ОА прочие`).

| Excel `Признак` | Роль в сверке | Домен | Таблица(ы) |
|-----------------|---------------|-------|-----------|
| **ОА** | RA (собственно отчёт) | `ra.ra_type = N'ОА'` | `ags.ra`, `ags.ra_summ` |
| **ОА прочие** | RA | `ra.ra_type = N'ОА, прочие'` (`mapToDomainRaType`) | те же |
| **ОА изм** | RC (изменение к базе) | строка `ags.ra_change`; тип базы — у связанного `ra` | `ags.ra_change`, `ags.ra_change_summ` |
| **ОА Аренда** | **не** в whitelist type=5 | параллель аренды земли | см. §6; type=3 / `ralp*` |

Отдельного Excel-признака «изм. к прочим» **нет**: все изменения идут как **«ОА изм»**; отнесение к капитальным / прочим — по **`ra_type` базы** после resolve (см. дерево лога type=5, задача 0053 / план 0707 §9.3.8).

**Префиксы номеров (эвристика файла 2026):** у «ОА прочие» часто литера **«П»** в буквенном блоке (`ГРП`, `СЗП`, `НБП`, `НПП`…); у обычных «ОА» — без неё (`ГР`, `СЗ`, `НБ`…). Не заменяет `ra_type` / признак.

## 2. Ветки ревизии type=5

| Ветка | Вход | Resolve | Apply (текущая модель) |
|-------|------|---------|-------------------------|
| **RA** | `ОА`, `ОА прочие` | период + № (+ прочие ключи матчинга) | insert/update `ags.ra` (+ суммы) |
| **RC** | `ОА изм` | разбор текста «Изм. N к \<база\> от …»; поиск базы по периоду+№ | insert/update `ags.ra_change` (+ `ra_change_summ`) |

Классификация RC в логе/дереве: по `ra_type` найденной базы (`ОА` vs `ОА, прочие`), не по отдельному Excel-знаку.

Идемпотентность staging (whitelist): повторный dry-run на том же файле даёт то же распределение признаков (см. план 0323, exec 106/107).

## 3. Многократное представление

**Явление:** один и тот же логический документ (изменение с тем же № к той же базе в том же отчётном периоде) проходит рассмотрение **несколько раз** — отдельные циклы поступления / СЗ / возврата с разными датами и письмами. В Excel это **несколько строк** «ОА изм» с одним номером изменения.

**Бизнес:** схлопывать в одну запись **нельзя** — нужна история представлений (подтверждено при разборе блокера R1.0).

**Где встречается**

| Тип документа | Носитель в БД | Модель «несколько подходов» | Статус относительно UX |
|---------------|---------------|------------------------------|-------------------------|
| Изменение к ОА (`ОА изм`) | `ags.ra_change` | сейчас **одна** строка на `(ra_period, rac_ra, rac_num)` | **конфликт** с явлением → блокер apply |
| Изменение к «ОА, прочие» | тот же `ra_change` | та же модель; в истории редко | тот же UX |
| РАЛП (аренда) | `ralpRa` + **`ralpRaAu`** | несколько Au на один ra | **поддерживается** (образец) |
| Собственно ОА / ОА прочие как база | `ags.ra` | одна строка отчёта на ключ периода+№ (как сейчас) | вне блокера RC |
| «ОА Аренда» в своде ОА | не в type=5 | факт живёт в контуре РАЛП | см. §6 |

**Не путать с:** несколькими **разными** номерами изменений (Изм. 1, Изм. 2) к одной базе; повторным прогоном ревизии (идемпотентность).

Статьи глоссария: «Многократное представление», «Уникальность изменения за период».

## 4. Блокер UX `ЗаПериодЗаОтчётОдинНомер`

| Поле | Значение (прогон 2026-11-19) |
|------|------------------------------|
| Симптом | `BatchUpdateException` / SQL Server **2601** duplicate key |
| UX / индекс | `ЗаПериодЗаОтчётОдинНомер` на `ags.ra_change` |
| Зерно ключа | `(ra_period, rac_ra, rac_num)` — пример падения: `(229, 113328, 2)` |
| Dry-run | exec **1225** — OK (NEW RC в т.ч. 72) |
| Apply | откат TX reconcile; `adtStatus` при этом мог остаться `COMPLETED` (хвост качества статуса) |
| Excel | ≥2 строки «ОА изм» с одним № изменения к одной базе в одном периоде (примеры строк файла: **12068/13073**, также **12066/13288**) |

**Вывод для фикса (ещё не выбран):** нужна модель, допускающая несколько представлений (по аналогии с `ralpRaAu`), либо иное зерно уникальности — **после** фиксации знаний в глоссарии/этом конспекте.

## 5. Изменения к «ОА, прочие»

### 5.1. Текущий свод ОА (staging ~exec 1226 / файл 2026)

Из ~535 строк «ОА изм»:

| Исход | Кол-во (порядок) |
|-------|------------------|
| Точное сопоставление с базой **«ОА»** в том же файле | **276** |
| Точное сопоставление с базой **«ОА прочие»** | **0** |
| База не в файле (часто периоды **2025** и раньше) | **254** |
| Не разобрал парсер | **5** |

В тексте изм. нет маркера «проч*»; префиксы баз — как у обычных ОА.

### 5.2. Историческая БД (`FishEye_prod_noM6`, 2026-11-19)

| `ra_type` базы | Строк `ra_change` | Баз с изменениями |
|----------------|-------------------|-------------------|
| `ОА` | 3045 | 1890 |
| `ОА, прочие` | **2** | 2 |

Примеры (по одной правке на базу, 2020–2021):

1. `НСК20п-2004398-2` → Изм. №1 (`rac_key` 27)  
2. `ГИП21-2004034-4` → Изм. №1 (`rac_key` 397)

Обе видны в `ags.RRcTimeList` с `typeGr = '2. ОА, прочие и Изм'`, `type = 'изм.'`.

**Форма:** та же таблица и поля жизненного цикла, что у изм. к «ОА»; отличие — тип базы и редкость (~0,07% изменений).

## 7. Участие в расчёте освоения `_2605`/`_2606`

Классификация в `ags.RRcTimeList` (и отчёт, и изменение):

```sql
iif(ra.ra_type = 'ОА, прочие', '2. ОА, прочие и Изм', '1. ОА и Изм.')
```

| Контур | `typeGr` | `typeGrTtl` | Куда в PercentBrn | Mstrg / лимит ИПГ |
|--------|----------|-------------|-------------------|-------------------|
| ОА + изм. к ОА | `1. ОА и Изм.` | план / неплан (`ag_*` / `np_*`) | капитальный | да (при схеме) |
| ОА прочие + изм. к ним | `2. ОА, прочие и Изм` | `4. Прочие` | **`oh_*`** | **нет** |

Следствие: если изм. к «ОА, прочие» снова появятся в Excel и попадут в `ra_change` (+ суммы), существующий код сверки и стек `_2605`/`_2606` отнесут их в **`oh_*`**, без отдельного Excel-признака.

Детали каскада: [09-scheme-cascade-mastering.md](../../sql/26-0604/docs/09-scheme-cascade-mastering.md) (слой D). Глоссарий: «Прочие затраты в отчёте (`oh_`)».

**Замечание:** set-based `fnMasteringRa*_2606` при скане `ra`/`ra_change` **не фильтрует** `ra_type`; в `fn2` ветка mastering жёстко помечена `typeGr = '1…'`. Документные суммы «прочих» в отчёте идут через `RRcTimeList` по `typeGr`. Возможное смешение stCost в mastering — отдельный исследовательский хвост, не блокер RC UX.
