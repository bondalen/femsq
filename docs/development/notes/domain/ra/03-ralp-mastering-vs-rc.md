> **Граница:** доработку стека **`_2605`** под multi-presentation RC **не планируем** (прод живёт; падений по этой причине нет; «до идеала» не цель). Ниже — как устроен РАЛП, и что из этого следует для RC / `_2606` / общих представлений.

---

## 1. Как считается РАЛП

### Модель данных

| Уровень | Таблица | Зерно | Сумма / статус |
|---------|--------|-------|----------------|
| Отчёт | `ralpRa` | `ralprKey` | номер, период Y/M, стройка |
| Представление | `ralpRaAu` | UX `(ralpraRa, ralpraArrived)` | `ralpraCostAndVat`, arrived/sent/returned, `ralpra_fdKey` |

### Ключевой приём: плоский VIEW

```sql
-- ags.ralp (живой на стенде)
SELECT r.…, a.ralpraKey, a.ralpraCostAndVat, a.ralpraArrived, a.ralpraSent, …
FROM ags.ralpRa r
JOIN ags.ralpRaAu a ON r.ralprKey = a.ralpraRa
```

**Одна строка VIEW = одно представление.** Несколько Au на один `ralpRa` → несколько строк с **разными** суммами и статусами. Расчёт **не** выбирает «последнее Au» и не схлопывает.

На noM6 (после apply type=3): `ralp_view_rows` = числу Au (каждая Au — отдельная единица факта).

### Потребители

| Стек | Как берёт РАЛП |
|------|----------------|
| Legacy mastering | `fnMasteringPresRalp` / Accp / … — `FROM ags.ralp`, сумма через `fnStCostRalp(ralpraKey, …)` |
| `_2606` mastering | `fnMasteringRalpCostBase_2606` — строки из `ags.ralp`; cost из `factDocCost` по `ralpra_fdKey` (stCost **150**) |
| `_2606` fn2 (документные колонки) | `SUM(ralpCostAndVat)` / статусы с `ags.ralp` |
| `_2605` | **своего** кода РАЛП нет: обёртка над `fnIpgChRsltCstUtl_2408` / тем же контуром, что уже читает `ags.ralp` |

Итог: multi-presentation для аренды **уже «вшито» в зерно VIEW**. Ни `_2605`, ни `_2606` не содержат отдельной ветки «несколько Au».

## 2. Контраст с текущим RC

| | РАЛП | `ra_change` сейчас |
|--|------|---------------------|
| Представления | N строк Au | 1 строка change |
| Сумма | на Au | версии в `ra_change_summ`, в отчёте — **latest** |
| Статус рассмотрения | на Au | на строке change |
| Вход расчёта | `ags.ralp` (развёртка) | `RRcTimeList` / `rac_key` + latest |

Поэтому блокер RC — не «расчёт не умеет N представлений», а **доменная модель RC не разворачивает представления**, в отличие от РАЛП.

## 3. Следствие для объёма правок расчёта

### Если целевая модель RC ≈ РАЛП (вариант A)

Паттерн: таблица представлений + (желательно) VIEW «change ⋈ presentation», суммы/статус на представлении.

| Объект | Типичный объём |
|--------|----------------|
| Reconcile type=5 + DDL Au | **основной** объём работ (1.4.3) |
| VIEW / правка `RRcTimeList` (ветка изм.) | точечно: развернуть N строк вместо 1 |
| `fnMasteringRa*_2606` | точечно: носитель = ключ представления (как `ralpraKey`), не только `rac_key` |
| `_2606` fn2 | обычно **без** отдельной логики, если питается обновлённым `RRcTimeList` / VIEW |
| **`_2605` пакет / `fn2_2605`** | **вне объёма**; отдельной переписки не требуется для R1.0 |

`_2605` косвенно увидит эффект **только если** поменять общее представление (`RRcTimeList` и т.п.), которым он уже пользуется. Это не «проект доработки `_2605`», а побочный эффект общего VIEW — его нужно учитывать при 1.4.2.3 (два экземпляра / Access), но **не** закладывать как отдельный трек полировки `_2605`.

### Вариант B (расширить UX на `ra_change`)

Расчёт по-прежнему видит одну строку; разные письма некуда деть без потери. Выигрыша «как у РАЛП» нет; правки mastering/`RRcTimeList` не спасают историю представлений.

---

## 4. Фиксация для плана

- Расчёт освоения для РАЛП **уже** суммирует каждое представление через `ags.ralp`.  
- Для RC эталон — тот же приём (развёртка), а не усложнение `_2605`.  
- **`_2605` не рассматриваем** как объект доработки под этот блокер.  
- В 1.4.2.2 сравнивать A/B с опорой на этот паттерн; влияние на общие VIEW — в 1.4.2.3.
