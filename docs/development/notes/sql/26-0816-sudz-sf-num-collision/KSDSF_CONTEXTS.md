## Цель

Один экран `SudzSfDoubleView` и очередь `sudz.CnInvUplSfDouble`, но **разные адаптеры** источника Excel / якоря суммы / части правил советника. Не подставлять поля `CnInvPmtUplTbl` в подписи и семантику `CnInvDbtUplTbl` через «тихие» SQL-алиасы.

## Суммы pmt (исследование до 1.8.5, 2026-09-28)

**Поля Excel:** `ciputCdtBlns` (кредит платежа), `ciputCnInvDocSum` (сумма документа СФ), `ciputBlns`. На @59 open: **13/18** `cdt=docSum`, **4/18** `cdt=0` (док есть), **1** без docSum.

**Почему нельзя копировать dbt-панели:** якорь свода — `cidutDebt` → `cn_inv_dbt` / `DbtValue`. У платежей `cidutDebt=null`; подстановка `ciputDbtBlns` даёт ложный 0 и шум. Прогон @59: **0/18** попаданий anchor→`dbt_ttl`/`dvTtl`.

**Что «совпадает» в данных @59:** суммы Excel часто равны строкам `ags.cn_inv_pm` **того же** `cn_inv_pm_upl=59` с **пустым** `cn_inv_key`/`cnInvKey` — это уже вставленный платёж воронки без СФ, а не доказательство «какой inv выбрать». Исторических pm (другой upl) с тем же cdt/docSum на кандидатах домена — **0**. У multi-inv по номеру кандидаты тоже **без** любых pm.

**Прогон ABS (2026-09-28, все 18 якорей open @59, вкл. 259158,76):**  
`ABS(dbt_ttl|dvTtl|cidutDebt)` — **0** (даже с округлением до рубля).  
`ABS(cdt|doc|blns)` в `cn_inv_pm` другого upl — **0**.  
Единственные попадания — orphan `cn_inv_pm` **того же** pm=59 (`cn_inv_key`/`cnInvKey` NULL); у 259158,76 это pm **576721**, `blns=-259158.76` (модуль совпал). Весь пакет pm=59: **15873** строк pm, **0** с привязанным inv.  
8/18 сумм очереди **нигде** в pm/долгах (только Excel Tbl) — InsPm для них ещё не оставил след с этой суммой.

**Вывод от 2026-09-28 (история, формула снята):** на пакете 59 сравнение одной строки очереди с `DbtValue` / `cn_inv_dbt` дало 0. Совпадения cdt/docSum с orphan `cn_inv_pm` того же пакета — идентичность платежа, не выбор СФ. Предложение якоря `cdt≠0 ? cdt : docSum` (**1.8.5a**) **снято** сверкой ниже.

## Суммы pmt — сверка со сводом (2026-09-30)

Портфельный свод **901** (на 31.12.2025, `yr_key=901`) и платежи того же каталога `excel/2025-12/debit`. Группировка платежей: `ciputUnloadKey` + `ciputCnInv` (присвоение). Итог = Σ `ciputBlns` (= Σ дебет − Σ кредит). Строки с нулевым сальдо итог не меняют.

| Пакет | Счёт | `g_p` → 901 | Долгов свода | Σ сальдо = `cidutDebt` |
|-------|------|-------------|--------------|------------------------|
| 59 `export_26-0130_767501` | 767501 | есть, key 20 | 7 | 7 |
| 57 `export_26-0130_606022` | 606022 | есть | 327 | 327 |
| 58 `export_26-0130_761010` | 761010 | есть | 9 | 9 |
| 60 `export_26-0211_767502` | 767502 | есть | 238 | 237 |

**580 / 581.** Исключение: пакет 60, СФ **90621**, договор 1559/2023, `cidutKey` 47757 — свод 3 000 000 (весь просрочен), Σ сальдо 2 500 000. |Σ кредит| = 3 000 000, то есть якорь «кредит» совпал бы ложно.

Счёт 761010 показывает, почему сумма документа не годится: `0519CR0004`, 87 строк, долг 30 404,40 = Σ сальдо, сумма документов 315 127,52; **0 из 9** равенств по документу. На однострочных СФ 606022 документ совпадает с сальдо и долгом одновременно — это не различитель.

Просрочка: колонки overdue Tbl платежей пустые. На 767501, 606022 и 761010 `cidutDebtOverdue` = 0. На 767502 39 долгов просрочены целиком, все со сроком раньше 31.12.2025; частичного разреза нет; 38 из 39 равны Σ сальдо.

**Реализовано (1.10.1–1.10.2, JAR 321):** итог сальдо на карточке (`pmtSfBlnsSum` / `pmtSfBlnsRows`) и запрос `sudzPmtSfSumCompare`: сравнение с `cidutDebt` связанного свода (тот же номер СФ и счёт ГК), рядом `cidutDebtOverdue`. Нет строки или несколько — явный исход, без автовыбора. Smoke @cius=1275 (СФ «94»): итог −259 158,76, 1 строка, «Строки свода нет.» Советник `pmt_blns_same_cn` (**1.10.4**) ещё не включён. Orphan `cn_inv_pm` того же пакета не использовать.

## История платёжного документа (1.11, JAR 323)

Код «№ докум.» уже лежащий в `cn_inv_doc` показывает прежние платежи и их `inv` / договор / счёт ГК. На очереди 17 у девяти строк прежний номер СФ другой; у «93» две прежние СФ; у «б/н» прежний договор другой. По всей истории **35 191** документ связан больше чем с одной `inv`, **1 359** — уже внутри одной выгрузки.

Лес (`FemsqWalkTree`, view list) в КСДСФ платежей стоит в нижней части колонки «Суммы» и отделён от сверки сплиттером. Между карточкой Excel и советником свой сплиттер — тот же в контексте свода. На выбранной СФ договора и слота долга лес остаётся под деревом СФ. Запросы `sudzPmDocForestByCius` и `sudzPmDocForestByInv`. Спокойная запись не ставится. Советник дописывает строку «Документы:» и не меняет action: на приёмке **1.9.6** действие по-прежнему по `sfByNum`.

**Центр кандидата СФ (план 1.14):** **1.14.1–1.14.6** ✅. @cius=1310: create inv **106724**; pm=59 перенесены на cias **113261**; legacy 40729 сохранил историю 23–24. Советник `suspicious_inv`; InsPm не матчит подозрительный №; create при open/repair created делает cias+перенос/вставку pm пакета. JAR **332**.

Smoke @cius=1275 (СФ «94»): документ 5400217611, пакет export_767501_25-0124, СФ ГИ241227-0009-36, договор КС-51, счёт 767501; action остался link на inv=23785. СФ «108»: прежних пакетов нет. СФ «93»: документы расходятся, автовыбор не делается. Договор КС-51, inv 78052: «Платёжные документы этой СФ: 1».

## API (после 1.8.1)

`SudzSfDoubleExcelCandidate.source`: `"dbt"` \| `"pmt"`.  
Для `pmt`: `cidutDebt` / `cidutDebtOverdue` **null** (не алиас с дебета); суммы платежа — поля `pmtCdtBlns`, `pmtCdtBlnsOverd`, `pmtDocSum`, `pmtBlns`. Ключ строки по-прежнему в `cidutKey` для совместимости GraphQL (= `ciputKey` при source=pmt); UI показывает подпись **ciputKey**.
