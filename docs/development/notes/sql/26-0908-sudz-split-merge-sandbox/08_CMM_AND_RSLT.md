## 1. Что не так сейчас

| Слой | Сейчас | Следствие при split/merge |
|------|--------|---------------------------|
| Идентичность долга | `Dbt` | один канон на всю историю — это правильно |
| Факт среза | `DbtValue` (слот×upl) | число строк на срезе **меняется** |
| Комментарий | `cnInvCmm*` → `*Dbt` / legacy `*InvAccnt`; группа = `cnicGroup` | текст **один на канон**, хотя группа уже «про период» |

`cnicGroup` / `yr_CmmGr` уже привязывают текст к **раунду**. Субъект раунда ошибочно = весь `Dbt`. После split на срезе две величины, а мероприятие всё ещё одно «на долг 111». После merge два исторических текста некуда посадить, кроме склейки.

Отсюда: **все комментарии раунда** (тексты, типы Ag/Cst/Dt/Fn и вхождения в именованные группы) вязать к **`DbtValue` (`dvKey`)**. Канон `Dbt` для них только выводится: Value → слот → `invDbtDbt`.

D3′ (`*Dbt` рядом с `*InvAccnt`) не отменяем: это мост Access. Следующий шаг той же линии — nullable `*Dv` → `DbtValue` (**S77 I4 / черновик `02_DRAFT_cmm_D3double_Dv.sql`**, не в пакете 01).

## 2. Без исключений на `Dbt`

`cnInvGr` («рассмотреть углубленно в сентябре» и аналоги) — **тот же слой**, что остальные cmm: привязка долга к группе внутри `cnInvCmmGr`, то есть к раунду/выгрузке. На каноне не оставляем: при split на срезе две Value — два вхождения (или одно, если оператор пометил только долю); при merge — вхождения едут со своими Value.

Куратор / код стройки / мероприятия — туда же, на `DbtValue`. Отдельного «годового якоря на Dbt» для cmm не заводим.

## 3. Канон Rslt — полосы A и C

**Зафиксировано 2026-09-08.** Опора — листы `A_111_curr202` и `C_111_curr210` в макете песочницы. Листы B, `111_timeline`, `112_canon_merge` — справочные, на них не опираемся.

### 3.1 Зерно ячеек

| Колонки | Зерно |
|---------|--------|
| Факты крайней выгрузки (СФ, договор, Ttl, Overd) | `DbtValue` **этой** upl (пример: крайняя **QI**) |
| «Погашено» | канон `Dbt` (`NULLIF(∑Overd_база − ∑Overd_срез, 0)`), **не** доля |
| «Старые» cmm (`yr_CmmGr`) | `DbtValue` **предшествующего** среза (пример: **QIV** при крайней QI). На рассылке специалистам новых ещё нет |
| `*_new` | не одно зерно на весь жизненный цикл файла — **два этапа** ниже |

`ags_Yr_DbtChangesRslt_*.xlsx` — два бизнес-процесса ([03 §1.1.1.3–1.1.2.2](../../domain/sudz/03-processes.md); `SudzRsltExcelExporter` сбор vs повтор; REST `rslt-sborn` / `rslt-povtor` + импорт в `yr_CmmGr_New`):

1. **Рассылка (Rslt сбор):** факты — крайняя upl; «старые» — предшествующий срез (`yr_CmmGr`); `*_new` **пустые** (`yr_CmmGr_New` не участвует). Специалисты читают QIV и пишут новые для QI.
2. **Возврат в БД и Rslt повтор:** `*_new` из Excel → `yr_CmmGr_New`; зерно новых = `DbtValue` **текущего** раунда (QI). D644 после вехи 1.1.3 читает `yr_CmmGr`.

Число строк полосы = max(зерно факта крайней upl, зерно старых cmm, зерно `*_new` если заполнены). Колонка с зерном 1 сливается на все строки полосы. Merge комментариев — не баг, а разное зерно соседних блоков (полоса A: факт QI split, старые QIV ещё целые).

### 3.2 Две формы (канон)

**A — крайний срез уже split** (`A_111_curr202`): две строки факта (2×18000); блок предшествующего целого среза и его мероприятия — одна ячейка на обе строки.

**C — крайний срез снова целый** (`C_111_curr210`): одна слитая ячейка факта 36000; «старые» мероприятия предшествующего split — две ячейки без merge.

### 3.3 Что из этого не следует прямо сейчас

- Не менять `SudzRsltExcelExporter` до **S77.5** (пока 1 строка на `Dbt`).
- I1–I3 на DEV `sudz` применены (S77.2). `02` (*Dv) и split 85166 — ещё нет.
- Якорь **85166** (КСДД 2807/2808 @901) — фикстура UAT **S77.6**, не закрывать Create/Link.

## 5. Решение (зафиксировано)

1. Все `cnInvCmm*` **и** `cnInvGr` — якорь на **`DbtValue`**. `Dbt` для cmm/gr только выводимый.  
2. В Rslt зерно комментариев = зерно Value среза группы; формы полосы — **A** и **C**. «Погашено» на каноне.  
3. Следующая работа продукта — **S77** (инварианты → DDL DEV → Split/Merge → воронка → экспортёр A/C → 85166 → `26-0505`). C.10 без S77 не закрывает зерно QIV/QI.
