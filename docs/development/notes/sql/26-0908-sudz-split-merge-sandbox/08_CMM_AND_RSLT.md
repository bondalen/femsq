## 1. Что не так сейчас

| Слой | Сейчас | Следствие при split/merge |
|------|--------|---------------------------|
| Идентичность долга | `Dbt` | один канон на всю историю — это правильно |
| Факт среза | `DbtValue` (слот×upl) | число строк на срезе **меняется** |
| Комментарий | `cnInvCmm*` → `*Dbt` / legacy `*InvAccnt`; группа = `cnicGroup` | текст **один на канон**, хотя группа уже «про период» |

`cnicGroup` / `yr_CmmGr` уже привязывают текст к **раунду**. Субъект раунда ошибочно = весь `Dbt`. После split на срезе две величины, а мероприятие всё ещё одно «на долг 111». После merge два исторических текста некуда посадить, кроме склейки.

Отсюда: **все комментарии раунда** (тексты, типы Ag/Cst/Dt/Fn и вхождения в именованные группы) вязать к **`DbtValue` (`dvKey`)**. Канон `Dbt` для них только выводится: Value → слот → `invDbtDbt`.

D3′ (`*Dbt` рядом с `*InvAccnt`) не отменяем: это мост Access. Nullable `*Dv` → `DbtValue` (**S77 I4 / `02_DRAFT_cmm_D3double_Dv.sql`**, DEV `sudz` 2026-09-09).

## 2. Без исключений на `Dbt`

`cnInvGr` («рассмотреть углубленно в сентябре» и аналоги) — **тот же слой**, что остальные cmm: привязка долга к группе внутри `cnInvCmmGr`, то есть к раунду/выгрузке. На каноне не оставляем: при split на срезе две Value — два вхождения (или одно, если оператор пометил только долю); при merge — вхождения едут со своими Value.

Куратор / код стройки / мероприятия — туда же, на `DbtValue`. Отдельного «годового якоря на Dbt» для cmm не заводим.

## 3. Канон Rslt — полосы A и C

**Зафиксировано 2026-09-08.** Опора — листы `A_111_curr202` и `C_111_curr210` в макете песочницы. Листы B, `111_timeline`, `112_canon_merge` — справочные, на них не опираемся.

### 3.1 Зерно ячеек

| Колонки | Зерно |
|---------|--------|
| Факты крайней выгрузки (СФ, договор, Ttl, Overd) | `DbtValue` **этой** upl (пример: крайняя **QI**) |
| «Погашено» | канон `Dbt` (`NULLIF(∑Overd_база − ∑Overd_срез, 0)`), **не** доля |
| «Старые» cmm (`yr_CmmGr`) | `DbtValue` **предшествующего** среза (пример: **QIV** при крайней QI). На рассылке специалистам новых ещё нет |
| `*_new` | не одно зерно на весь жизненный цикл файла — **два этапа** ниже |

`ags_Yr_DbtChangesRslt_*.xlsx` — два бизнес-процесса ([03 §1.1.1.3–1.1.2.2](../../domain/sudz/03-processes.md); `SudzRsltExcelExporter` сбор vs повтор; REST `rslt-sborn` / `rslt-povtor` + импорт в `yr_CmmGr_New`):

1. **Рассылка (Rslt сбор):** факты — крайняя upl; «старые» — предшествующий срез (`yr_CmmGr`); `*_new` **пустые** (`yr_CmmGr_New` не участвует). Специалисты читают QIV и пишут новые для QI.
2. **Возврат в БД и Rslt повтор:** `*_new` из Excel → `yr_CmmGr_New`; зерно новых = `DbtValue` **текущего** раунда (QI). D644 после вехи 1.1.3 читает `yr_CmmGr`.

Число строк полосы = max(зерно факта крайней upl, зерно старых cmm, зерно `*_new` если заполнены). Колонка с зерном 1 сливается на все строки полосы. Merge комментариев — не баг, а разное зерно соседних блоков (полоса A: факт QI split, старые QIV ещё целые).

**Порядок колонок FEMSQ (2026-10-15):** «старые» cmm стоят **сразу после фактов предшествующего среза**; факты крайней upl — следующей группой; `*_new` — в самом конце после крайней группы. Access-эталоны (`26-0212`, `26-0505`) кладут куратора/мероприятия в хвост после всех дат — FEMSQ сознательно расходится, чтобы зерно merge не отрывалось от квартала. Сверка с эталоном — по техн. именам и зерну, не по индексу колонки. При 3+ срезах блок «старых» один (у предшествующего к крайней). Заливка row2 «старых» — цвет предшествующего квартала.

### 3.2 Две формы (канон)

**A — крайний срез уже split** (`A_111_curr202`): две строки факта (2×18000); блок предшествующего целого среза **и сразу за ним** его мероприятия — одна ячейка на обе строки; затем факты крайней; в конце пустые `*_new` по зерну крайней.

**C — крайний срез снова целый** (`C_111_curr210`): одна слитая ячейка факта 36000; «старые» мероприятия предшествующего split — две ячейки без merge **рядом с** фактами предшествующего.

### 3.3 Что из этого не следует прямо сейчас

- **S77.5:** экспортёр и предпросмотр пишут полосу **A** (N строк факта = N Value среза; «погашено» и колонки зерна 1 — merge). Полоса **C** — после того, как экспортёр читает `*Dv` (backfill stage1 на DEV есть).
- I1–I4 на DEV `sudz` применены (`01` S77.2; `02` *Dv + `04` backfill 2026-09-09). `ags` / `test_sudz` / prod не трогали.
- Якорь **85166** (слоты 13041/13042, ciud 2807/2808 `created`, G4 `open=0`) — Split **S77.6** уже в живом `sudz`; Create/Link не вызывать повторно.

## 4. Песочница

Схема `test_sudz_sm`, скрипты `09`–`12`. Повтор макетов: `python3 …/apply_sm.py --xlsx`.

## 5. Решение (зафиксировано)

1. Все `cnInvCmm*` **и** `cnInvGr` — якорь на **`DbtValue`**. `Dbt` для cmm/gr только выводимый.  
2. В Rslt зерно комментариев = зерно Value среза группы; формы полосы — **A** и **C**. «Погашено» на каноне.  
3. Следующая работа продукта — **S77** (инварианты → DDL DEV → Split/Merge → воронка → экспортёр A/C → 85166 → `26-0505`). C.10 без S77 не закрывает зерно QIV/QI.

## 6. Чтение возврата, пока комментарий на каноне `Dbt`

**Зафиксировано 2026-10-12; запись `*Dv` — 2026-10-14 (узлы 3.2–3.3).** GraphQL и DAO пишут `cnInvCmm` / `cnInvCmmCst` с якорем `*Dv`; `*Dbt`/`*InvAccnt` выводятся из Value → слот → `invDbtDbt`. На DEV — filtered UNIQUE `(группа, тип, *Dv)`.

Возврат читает лист Rslt, строка 3 — техн. имена `dbtKey`, `cur_new`, `mery_new`, `cstAgPn_new`. Колонка «Проверено» не читается. Д644 и Свод в этот разбор не входят.

С 2026-10-14 (узел **3.4**) экспортёр Rslt читает `*Dv` на Value: «старые» — предшествующий срез, `*_new` — крайняя upl; пустые `*_new` в сборе — по ячейке на Value крайней.

Разбор файла (`SudzRsltReturnImporter`, с 2026-10-14) сохраняет строки полосы с `bandOrdinal` и пишет непустые `*_new` на Value **крайней upl** года (`ORDER BY idNum`):

| Вид листа | Что делает разбор / запись |
|-----------|-------------------|
| Одна строка, без склейки | Текст → все Value крайней upl этого долга |
| Полоса: тот же ключ и тот же текст | N строк полосы → N Value по ординалу (один текст) |
| Полоса после сохранения в Excel: слитая колонка только сверху | Текст верхней ячейки протягивается; ординалы сохраняются |
| Разные непустые тексты одной колонки на полосе | Каждая строка → своя Value по ординалу |
| Формула кода (`=AWxx`) | Берётся вычисленное значение |

Пустая ячейка `*_new` уже записанный текст долга не снимает.

## 7. Полоса исходящего Д644

**Факты полосы зафиксированы 2026-10-13; зерно комментария уточнено 2026-10-14** (узел 3 плана [chat-plan-26-1012](../../chats/chat-plan/chat-plan-26-1012-qii-cmm-d644.md)). Документ показывает состояние долгов базового свода года (`Overd` базы > 0). Высота полосы долга — `max(число долей базы, число долей среза)`.

Доли стыкуются так: сначала общий слот `dvInvDbt`, затем оставшиеся доли по порядку `idNum`. Одна доля базы и одна доля среза остаются одной строкой, даже если между выгрузками сменился ключ `invDbt`. Соединение всех долей базы со всеми долями среза по одному `dbtKey` не применяется. Строки одного `dbtKey` в выдаче идут подряд (`ORDER BY` счёта, контрагента, `dbtKey`, номера в полосе); отдельно «сдвигать» доли не нужно.

| База | Срез | Колонки базы | Колонки среза | Комментарий, код, агент |
|------|------|--------------|---------------|-------------------------|
| 1 | 1 | одна | одна | один |
| 1 | 2 | одна ячейка на всю полосу | две отдельные | **два** (судьбы долей после split могут разойтись) |
| 2 | 1 | каждая доля своя | одна ячейка на всю полосу | **один** слит на полосу (не повторять текст) |
| 2 | 2 | каждая доля своя | каждая доля своя | два по парам слотов; одинаковый текст — две ячейки |

После якоря на `DbtValue` колонки комментария, кода стройки и агента читают Value официальной группы раунда (`yr_CmmGr`). В Д644 закрытия раунда это обычно Value **среза**: специалисты уточняли позиции на крайней выгрузке. Зерно 1 сливается вниз (`_base_span`, `_curr_span`, `_cmm_span`). «Погашено» — одна ячейка на полосу: `NULLIF(сумма просрочки базы − сумма просрочки среза, 0)`.

С 2026-10-14 (узел **3.4**): процедура `Yr_DbtChangesD644` читает комментарий/код по `*Dv` Value среза (fallback `InvAccnt`); `cmm_span` = зерно среза (как `_curr_span`).

**Walk-back (2026-10-15):** если на крайней upl нет Value, запись cmm идёт на Value последней предшествующей upl того же года (часто база). В Д644: `COALESCE(*Dv среза, *Dv базы, Acc)`; `_cmm_span` = зерно фактического якоря (`curr_span` или `base_span`). Пустые `*_new` в Rslt сбор — по числу Value walk-back upl. Acc — только если Value в году нет. DAO: `findValueBindOnYearWalkBack` / `findValueKeysForDbtOnGroupUpl`; протокол импорта: `boundExtreme` / `boundWalkBack` / `boundAcc`.

| База | Срез | Куда писать *_new | Показ Д644 |
|------|------|-------------------|------------|
| есть | есть | Value среза | curr_span |
| есть | нет | Value базы (walk-back) | base_span |
| нет | — | Acc (last resort) | base_span, если строка есть |

**Миграция DEV (узел 3.5, 2026-10-14):** группа **907** — Acc→`*Dv` на Value крайних upl годов, смотрящих на группу (901→903, 909→914); при нескольких Value — копии текста на каждую долю. Скрипт `06_MIGRATE_cmm_Dv_group_907.sql`. Группы 905/906 и прод не трогались.

**Миграция DEV (2026-10-15):** группа **1909** — Acc→`*Dv` walk-back (`07_MIGRATE_cmm_Dv_group_1909_walkback.sql`). После: Д644 901/903 filled **176**.

**Rslt сбор** после `*Dv`: факты крайней upl — Value крайней; «старые» cmm — Value предшествующего среза группы; пустые `*_new` — **по одной ячейке на Value крайней** (не сливать), чтобы можно было вписать разный текст на доли.

На годе 901 и срезе 903 (2026-10-13) полоса из двух долей с обеих сторон — долг **11897**: две строки по 18 000, сумма 36 000. Сводка `sudz.Yr_DbtChangesD644Svod` складывает доли долга до вычитания. Годовой свод по-прежнему не сдаётся как отчёт квартала. Проверочная книга года 909 (после узла 2) и отправка Д644 QII — 2026-10-14.
