## О файле project-development.json v2.0

**Назначение:** Планирование разработки с разделением задач (что делать) и структуры (как организовано).

**Ключевые изменения v2.0:**
- Разделение задач и структурных пунктов
- Поддержка DAG (Directed Acyclic Graph) - задача может быть в нескольких местах структуры
- Компактная навигация благодаря обёрткам (`task`, `task-item`, `tree`) + `*-attributes` + `task-items`
- Номера деревьев в структурных номерах пунктов
- Эмодзи и статусы в displayName для визуальной индикации
- Фокус на критериях завершения вместо оценки времени (для solo-разработчика)

## Архитектура данных

### Основные сущности

#### 1. Задача (Task)
**Назначение:** Описание того, что нужно сделать (единственный источник истины).

**ID:** Сквозная нумерация `0001`, `0002`, `0003`...

**Обязательные поля:**
- `displayName` - отображаемое имя с контекстом
- `task-attributes` - узел атрибутов задачи
  - `status` - текущий статус
  - `priority` - приоритет
  - `owner` - ответственный
  - `completionCriteria` - критерии завершения (массив)
  - `description` - описание задачи
  - `links` - ссылки на другие документы
  - `created` - дата создания
  - `lastUpdated` - дата последнего обновления

**Опциональные поля:**
- `extendedDescriptions` - ссылки на детальные описания в отдельных файлах

#### 2. Пункт структуры задач (Task Item)
**Назначение:** Позиция задачи в иерархической структуре (для навигации).

**ID:** Структурный номер с номером дерева `01.01.01`, `02.01`, `0a.01.01`

**Три обязательных элемента:**
1. **displayName** - для быстрого просмотра в свернутом виде (с эмодзи статуса)
2. **item-attributes** - все атрибуты пункта (свернутый узел)
3. **task-items** - массив вложенных пунктов

**Поля в item-attributes:**
- `structureId` - структурный номер (01.01.01)
- `taskId` - ссылка на задачу (0001) или null
- `positionInParent` - порядковый номер в родителе
- `comment` - опциональный комментарий

#### 3. Дерево задач (Tree)
**Назначение:** Корень организационного дерева с пунктами.

**Обязательные элементы:**
1. **displayName** - название дерева с номером
2. **tree-attributes** - атрибуты дерева
3. **task-items** - массив корневых пунктов

**Поля в tree-attributes:**
- `treeNumber` - номер дерева (01-zz)
- `treeId` - ID для программного доступа
- `type` - тип дерева (artifacts, features, modules, custom)
- `description` - описание назначения дерева
- `positionInParent` - позиция среди деревьев

## Правила работы со структурой

### Создание новой задачи

#### Шаг 1: Добавить задачу в tasks.items

```json
"0007": {
  "task": {
    "displayName": "Новая задача (pending, high). № 0007",
    "task-attributes": {
      "status": "pending",
      "priority": "high",
      "owner": "Александр",
      "completionCriteria": [
        "Класс создан",
        "Тесты написаны"
      ],
      "description": "Что нужно сделать",
      "links": {
        "projectDocsRefs": ["class:backend.database-config.DatabaseConfigService"],
        "journalRefs": ["chat:chat-2025-10-09-001"],
        "aiRuleRefs": []
      },
      "created": "2025-10-09",
      "lastUpdated": "2025-10-09"
    }
  }
}
```

#### Шаг 2: Обновить tasks.nextTaskId

```json
"nextTaskId": "0008"
```

#### Шаг 3: Добавить пункт в нужное дерево

Найти родительский пункт в `structure.trees` и добавить в его `task-items`:

```json
{
  "task-item": {
    "displayName": "⏳ Новая задача (pending, high). № 01.03 → 0007",
    "item-attributes": {
      "structureId": "01.03",
      "taskId": "0007",
      "positionInParent": 3
    },
    "task-items": []
  }
}
```

### Создание связи между деревьями (DAG)

Если задача должна быть в нескольких местах:

1. **В дереве артефактов:**
```json
{
  "task-item": {
    "displayName": "⏳ DatabaseConfigService (pending, critical). № 01.01.01 → 0004",
    "item-attributes": {
      "structureId": "01.01.01",
      "taskId": "0004",
      "positionInParent": 1
    },
    "task-items": []
  }
}
```

2. **В дереве функционала:**
```json
{
  "task-item": {
    "displayName": "⏳ Загрузка конфигурации (pending, critical). № 02.01.01 → 0004",
    "item-attributes": {
      "structureId": "02.01.01",
      "taskId": "0004",
      "positionInParent": 1,
      "comment": "Та же задача 0004 из дерева артефактов"
    },
    "task-items": []
  }
}
```

**Результат:** Задача `0004` появляется в двух деревьях с разными структурными номерами, но описана один раз.

## Типы деревьев

### 1. Дерево артефактов (artifacts)

**Назначение:** Иерархия модулей, компонентов, классов по структуре кода.

**Номер дерева:** `01`

**Нумерация пунктов:**
- Модули: `01.01`, `01.02`, `01.0a`
- Компоненты: `01.01.01`, `01.01.02`
- Классы: `01.01.01.01`
- Методы: `01.01.01.01.01`

**Пример:**
```
01                     Дерево артефактов
├── 01.01              Backend модуль
│   ├── 01.01.01       Модуль конфигурации
│   │   └── 01.01.01.01   DatabaseConfigService
│   └── 01.01.02       Модуль подключения
│       └── 01.01.02.01   ConnectionManager
└── 01.02              Frontend модуль
```

### 2. Дерево функционала (features)

**Назначение:** Иерархия функциональных возможностей системы.

**Номер дерева:** `02`

**Нумерация пунктов:** `02.01`, `02.01.01`, `02.01.01.01`

**Пример:**
```
02                     Дерево функционала
├── 02.01              Подключение к БД
│   ├── 02.01.01       Загрузка конфигурации → задача 0004
│   └── 02.01.02       Установка соединения → задача 0005
├── 02.02              CRUD операции
└── 02.0a              Аутентификация
```

### 3. Дерево модулей архитектуры (modules)

**Назначение:** Группировка по архитектурным модулям.

**Номер дерева:** `0a`

**Нумерация пунктов:** `0a.01`, `0a.02`, `0a.01.01`

**Пример:**
```
0a                     Дерево модулей
├── 0a.01              Database модуль
│   ├── 0a.01.01       Конфигурация → задача 0004
│   └── 0a.01.02       Подключение → задача 0005
├── 0a.02              API модуль
└── 0a.03              UI модуль
```

### 4. Пользовательские деревья

Можно создавать любые другие деревья по необходимости:
- `03` - По фазам разработки
- `04` - По приоритетам
- `05` - По ответственным
- `0b`, `0c`, и т.д.

## Правила нумерации

### Номера деревьев

**Формат:** По правилам из `project-documentation-rules-structural-numbering.md`

```
01-09    первые 9 деревьев
0a-0z    деревья 10-35 (буква после цифры 0)
1a-1z    деревья 36-61 (буква после цифры 1)
...
9a-9z    деревья 270-295
a0-a9    деревья 296-305 (буква перед цифрой)
aa-az    деревья 306-331
...
zz       последнее возможное дерево (1295)
```

### Структурные номера пунктов

**Формат:** `[treeNumber].[localNumber].[localNumber]...`

Где:
- `treeNumber` - номер дерева (01-zz)
- `localNumber` - локальный номер в родительском пункте (01-zz)

**Примеры:**

**Дерево 01 (артефакты):**
- `01.01` - первый пункт в дереве 01
- `01.01.01` - первый подпункт
- `01.01.01.01` - первый подподпункт

**Дерево 02 (функционал):**
- `02.01` - первый пункт в дереве 02
- `02.01.01` - первый подпункт

**Дерево 0a (модули):**
- `0a.01` - первый пункт в дереве 0a
- `0a.01.01` - первый подпункт

### ID задач

**Формат:** `0001`, `0002`, `0003`... (сквозная нумерация)

**Правила:**
- Начинается с `0001`
- Присваивается по возрастанию
- Не зависит от структурного номера
- Используется `tasks.nextTaskId` для отслеживания

## Синхронизация статусов между задачами и пунктами

### Правило автоматического обновления

При изменении статуса задачи **ОБЯЗАТЕЛЬНО** обновить `displayName` во всех пунктах структуры, ссылающихся на эту задачу.

### Формат displayName пункта

```
[emoji] [Название задачи] (status, priority). № [structureId] → [taskId]
```

**Пример:**
```
⏳ DatabaseConfigService класс (pending, critical). № 01.01.01.01 → 0004
```

**Компоненты:**
- `⏳` - эмодзи статуса (визуальная индикация)
- `DatabaseConfigService класс` - название из задачи
- `(pending, critical)` - статус и приоритет
- `№ 01.01.01.01` - структурный номер пункта
- `→ 0004` - ссылка на ID задачи

### Карта эмодзи статусов

| Статус | Эмодзи | Описание |
|--------|--------|----------|
| `pending` | ⏳ | Ожидает выполнения |
| `in-progress` | 🔄 | В работе |
| `paused` | ⏸ | На паузе (вне текущего фокуса; причина — в плане/дорожной карте) |
| `completed` | ✅ | Завершена |
| `blocked` | 🚫 | Заблокирована |
| `cancelled` | ❌ | Отменена |

### Алгоритм обновления статусов

1. **Изменить `status`** в `tasks.items[taskId].task['task-attributes'].status`
2. **Обновить `displayName`** в задаче
3. **Обновить `lastUpdated`** в задаче
4. **Найти все пункты** с `taskId` равным ID задачи
5. **Обновить `displayName`** в каждом найденном пункте
6. **Сохранить изменения**

### Пример обновления статуса

#### До изменения (pending)

```json
// Задача
"0004": {
  "task": {
    "displayName": "DatabaseConfigService класс (pending, critical). № 0004",
    "task-attributes": {
      "status": "pending"
    }
  }
}

// Пункт в дереве 01
{
  "displayName": "⏳ DatabaseConfigService класс (pending, critical). № 01.01.01.01 → 0004"
}

// Пункт в дереве 02
{
  "displayName": "⏳ Загрузка конфигурации (pending, critical). № 02.01.01 → 0004"
}
```

#### После изменения (in-progress)

```json
// Задача
"0004": {
  "task": {
    "displayName": "DatabaseConfigService класс (in-progress, critical). № 0004",
    "task-attributes": {
      "status": "in-progress",
      "lastUpdated": "2025-10-09T14:30:00Z"
    }
  }
}

// Пункт в дереве 01 - ОБНОВЛЕН
{
  "displayName": "🔄 DatabaseConfigService класс (in-progress, critical). № 01.01.01.01 → 0004"
}

// Пункт в дереве 02 - ОБНОВЛЕН
{
  "displayName": "🔄 Загрузка конфигурации (in-progress, critical). № 02.01.01 → 0004"
}
```

## Статусы задач

### Основные статусы (упрощенные для solo-разработчика)

- **pending** ⏳ - ожидает выполнения
- **in-progress** 🔄 - в работе (только одна-две задачи одновременно)
- **completed** ✅ - завершена (все критерии выполнены)
- **paused** ⏸ - на паузе (например, отложена до следующего горизонта дорожной карты)
- **blocked** 🚫 - заблокирована (указать причину в журнале)
- **cancelled** ❌ - отменена

### Правила смены статусов

```
pending → in-progress → completed
         ↓
      blocked → in-progress → completed
         ↓
      cancelled
```

**Важно:** Задача переходит в `completed` только когда все `completionCriteria` выполнены.

## Приоритеты

### Уровни приоритетов

- **critical** ⚠️ - критический (блокирует дальнейшую работу)
- **high** 🔴 - высокий (важно сделать скоро)
- **medium** 🟡 - средний (нормальный приоритет)
- **low** 🟢 - низкий (можно отложить)

### Правила приоритизации

Для solo-разработчика:
1. **critical** - делать в первую очередь
2. **high** - делать после critical
3. **medium** - делать в обычном порядке
4. **low** - делать когда есть время

## Критерии завершения (Completion Criteria)

### Вместо оценки времени

**Старый подход (v1.0):**
```json
"estimate": "8h",
"actualTime": "7h"
```

**Новый подход (v2.0):**
```json
"completionCriteria": [
  "Класс создан в правильном пакете",
  "Основные методы реализованы",
  "Unit-тесты написаны и проходят",
  "Документация JavaDoc добавлена"
]
```

### Правила формулирования критериев

✅ **Хорошие критерии:**
- Конкретные и проверяемые
- Описывают результат, а не процесс
- Можно однозначно сказать "выполнено" или "не выполнено"

❌ **Плохие критерии:**
- Абстрактные ("сделать хорошо")
- Про процесс ("поработать над...")
- Неясные ("почти готово")

### Примеры критериев

**Для создания класса:**
```json
"completionCriteria": [
  "Файл создан: src/main/java/.../ClassName.java",
  "Класс компилируется без ошибок",
  "Все публичные методы реализованы",
  "Unit-тесты покрывают основные сценарии",
  "JavaDoc документация добавлена"
]
```

**Для функционала:**
```json
"completionCriteria": [
  "Пользователь может успешно подключиться к БД",
  "Конфигурация загружается из properties",
  "Обработка ошибок работает корректно",
  "Автоматический reconnect при потере связи"
]
```

## Workflow для solo-разработчика

### Начало работы над задачей

1. **Найти задачу** в `tasks.items` по ID
2. **Перевести в `in-progress`**
3. **Обновить `displayName`** задачи и всех связанных пунктов
4. **Обновить `lastUpdated`**
5. **Создать чат в журнале** (project-journal.json)
6. **Начать работу**

### В процессе работы

1. **Добавлять логи** в журнал по мере выполнения
2. **Отмечать выполненные критерии** (можно в журнале)
3. **Обновлять статус** при необходимости

### Завершение задачи

1. **Проверить все `completionCriteria`**
2. **Перевести в `completed`**
3. **Обновить `displayName`** задачи и всех связанных пунктов
4. **Обновить `lastUpdated`**
5. **Добавить финальный лог** в журнал с отметкой выполненных критериев

### Работа с блокерами

1. **Перевести в `blocked`**
2. **Указать причину** в журнале
3. **Обновить `displayName`** с 🚫
4. **Создать задачу** для разблокировки (если нужно)
5. **После разблокировки** → вернуть в `in-progress`

### Поиск задачи

1. **По ID задачи:** Найти в `tasks.items[ID]`
2. **По структурному номеру:** Найти в соответствующем дереве
3. **Все места задачи:** Поиск `taskId` по всем деревьям

### Получение полной информации

```javascript
// Псевдокод
function getFullTaskInfo(structureId) {
  // 1. Разбираем структурный номер
  const treeNumber = structureId.split('.')[0];
  
  // 2. Находим дерево
  const tree = structure.trees.find(
    t => t.tree['tree-attributes'].treeNumber === treeNumber
  );
  
  // 3. Находим пункт в дереве
  const item = findItemInTree(tree, structureId);
  
  // 4. Получаем задачу
  const taskId = item['task-item']['item-attributes'].taskId;
  const task = tasks.items[taskId];
  
  return { item, task };
}
```

## Проверка целостности (Validation)

### Обязательные проверки

#### 1. Все taskId существуют
```
Для каждого пункта структуры:
  Если taskId не null:
    Проверить: tasks.items[taskId] существует
```

#### 2. Структурные ID уникальны глобально
```
Собрать все structureId из всех деревьев
Проверить: нет дубликатов
```

#### 3. positionInParent корректны
```
Для каждого родительского пункта:
  positions = [child.positionInParent для child в task-items]
  Проверить: positions = [1, 2, 3, ..., N] без пропусков
```

#### 4. tasks.nextTaskId корректен
```
maxTaskId = max(tasks.items.keys())
Проверить: nextTaskId > maxTaskId
```

#### 5. Синхронизация displayName
```
Для каждого пункта:
  task = tasks.items[пункт.taskId]
  Проверить: статус в displayName пункта совпадает со статусом задачи
```

### Опциональные проверки

- Все задачи используются хотя бы в одном дереве
- Нет циклических ссылок (если появится поддержка predecessors)
- Критерии завершения не пустые
- Ссылки в links существуют

## Заключение

Данная структура обеспечивает:
- ✅ **Единственный источник истины** - задача описана один раз
- ✅ **Гибкость организации** - DAG с множественными связями
- ✅ **Удобная навигация** - компактные displayName + свернутые attributes
- ✅ **Визуальная индикация** - эмодзи статусов для быстрого сканирования
- ✅ **Номера деревьев** - структурные номера включают номер дерева
- ✅ **Автоматическая синхронизация** - статус обновляется во всех связанных пунктах
- ✅ **Простота для solo** - фокус на критериях, минимум overhead
- ✅ **Масштабируемость** - легко добавлять новые деревья

### Ключевые преимущества

1. **Разделение ответственности:**
   - Task = ЧТО делать (содержание)
   - Task Item = ГДЕ в иерархии (навигация)

2. **Поддержка DAG:**
   - Одна задача → множество мест в структуре
   - Избегание дублирования описаний

3. **Компактность:**
   - Три элемента пункта: displayName + item-attributes + task-items
   - При свертывании виден только displayName с эмодзи

4. **Прослеживаемость:**
   - От структурного номера к задаче
   - От задачи к всем её местам
   - Визуальный статус везде одинаковый

5. **Масштабируемость:**
   - До 1295 деревьев верхнего уровня
   - Бесконечная вложенность пунктов
   - Гибкая классификация задач
